# Платежи CrustCaper через Flutterwave

Сервер использует Flutterwave Standard V3 для оплаты заказа на странице провайдера. Сумма берётся из подтверждённого заказа в целых RWF. Flutterwave требует адрес электронной почты покупателя и принимает телефон в международном формате. Реквизиты оплаты остаются на стороне провайдера. [Flutterwave Checkout API](https://developer.flutterwave.com/api/charge/standard)

## Среды и секреты

| Среда | Профиль Spring | `crustcaper.payment.provider` | Режим |
| --- | --- | --- | --- |
| Локальная | `local` | `local` | Изолированная симуляция. Провайдер возвращает пустой `checkoutUrl`. Локальный API результата ограничен профилем и владельцем заказа. |
| Стенд | `stage` | `flutterwave` | Flutterwave Test с отдельными стендовыми адресом возврата, секретами и данными. |
| Продакшен | `production` или `prod` | `flutterwave` | Flutterwave Live с отдельными адресом возврата, секретами и базой. |

За пределами локального профиля сервер по умолчанию выбирает `flutterwave`. Для запуска явно задайте `stage` или `production` (синоним `prod`) в `SPRING_PROFILES_ACTIVE`. Сервер отклоняет смешение стендового и боевого профилей, а также подключение Flutterwave при активном `local`, `demo` или `test`. Локальный адаптер недоступен при активном `stage`, `production` или `prod`. Параметр провайдера можно передать через `CRUSTCAPER_PAYMENT_PROVIDER`.

- `FLUTTERWAVE_SECRET_KEY` поступает через окружение сервера. Для `stage` нужен ключ режима Test, для `production` или `prod` — ключ Live. [Аутентификация Flutterwave V3](https://developer.flutterwave.com/docs/authentication)
- `CRUSTCAPER_FLUTTERWAVE_PAYMENT_OPTIONS` перечисляет разрешённые способы оплаты для этой среды. Укажите `card`, `mobilemoneyrwanda` или `card,mobilemoneyrwanda`. Сервер останавливает запуск при пустом списке, повторе или неизвестном значении. Отключите в кабинете Flutterwave **Enable Dashboard Payment Options**, чтобы применялся список из запроса. На подключённой проверке сверьте фактический набор способов оплаты на странице провайдера. [Способы оплаты Flutterwave V3](https://developer.flutterwave.com/docs/collections-inflow/payment-methods)
- `FLUTTERWAVE_WEBHOOK_SECRET` совпадает со случайным секретом webhook в панели соответствующей среды. Секрет состоит из 24–256 печатных ASCII-символов без пробелов.
- `CRUST_PAYMENT_RETURN_URL` содержит адрес HTTPS для возврата после оплаты без параметров или фрагмента. Сервер добавляет `orderId`, а Flutterwave добавляет параметры результата. Домен и публичный маршрут приложения назначает владелец среды.

Ключи передаются службе через хранилище секретов. В клиентскую сборку и журналы исключаются ключ, заголовок webhook, телефон, email, токен сессии и платёжная ссылка. [Аутентификация Flutterwave](https://developer.flutterwave.com/docs/authentication)

## Открытие и сверка оплаты

1. Сервер сохраняет попытку и сопоставляет её идентификатор с `tx_ref`. После сохранения вызывает `POST /v3/payments` с актуальным итогом, валютой, контактом и сроком брони в `link_expiration`. Ссылка принимается только с HTTPS-хоста `checkout.flutterwave.com` по пути `/v3/hosted/pay/…`.
2. Сервер получает `POST /api/v1/webhooks/flutterwave` и сравнивает `verif-hash` с секретом Standard V3. Событие даёт идентификатор для `GET /v3/transactions/{id}/verify`. При пропавшем клиентском возврате или webhook сервер может искать транзакцию по сохранённому `tx_ref`. [Webhooks V3](https://developer.flutterwave.com/docs/webhooks) · [Поиск по `tx_ref`](https://developer.flutterwave.com/api/transactions/verify-transaction-with-tx-ref)
3. Подтверждение заказа использует проверенный статус `successful`, точный `tx_ref`, уникальный идентификатор транзакции, номинальную сумму и валюту заказа. Фактически списанная `charged_amount` должна покрывать номинальную сумму. Итог записывается атомарно. Параметры перенаправления сообщают маршрут возврата. Исход показывает только сервер. [Сверка транзакции](https://developer.flutterwave.com/docs/transaction-verification)

Один `failed` от Flutterwave может относиться к попытке внутри ещё открытой hosted-страницы. В течение брони клиент возвращается к существующей ссылке. После неопределённого ответа на `POST /payments` сервер сохраняет исходную попытку для сверки. Повтор с тем же ключом возвращает её без нового запроса открытия. Покупатель может обновить статус того же платежа. Запрос статуса сохраняет последнее подтверждённое состояние при ответе с несовпадающей суммой или валютой. Вебхук для такого подтверждения возвращает `409`.

Если соединение не установилось до первой записи тела запроса, сервер закрывает эту попытку и сохраняет заказ в действующей брони. Покупатель может явно начать новую попытку. Если бронь истекла или проверка входных данных отклонила платёж до отправки, сервер закрывает заказ и освобождает слот. Статус по `tx_ref` и обработка позднего подтверждения защищают от повторной выдачи. [Повторы и сроки hosted checkout](https://developer.flutterwave.com/docs/collections-inflow/flutterwave-standard) · [Таймауты провайдера](https://developer.flutterwave.com/docs/error-timeouts)

## Сверка в фоне

В профиле Flutterwave Spring проверяет незавершённые попытки по `tx_ref` независимо от запуска приложения и доставки webhook. Реплики делят очередь через PostgreSQL, а запрос покупателя и фоновая проверка используют одно время последнего запроса. Привязка суммы, валюты и окна выдачи проверяется тем же методом, что и для webhook. Подтверждение после истечения брони попадает менеджеру на разбор.

Один запуск проверяет до двух попыток, новый запуск начинается через 15 секунд после завершения предыдущего. Интервал повторной проверки растёт с возрастом брони. Через 48 часов после окончания брони фоновая сверка завершается. Webhook и запрос статуса владельцем заказа продолжают действовать. При инциденте владелец стенда может отключить фоновую сверку переменной `CRUSTCAPER_PAYMENT_RECONCILIATION_ENABLED=false` и перезапуском API. Счётчик `crustcaper.payments.reconciliation` различает подтверждение, ожидание, ошибку провайдера и отклонённый ответ без идентификаторов заказов или платежей.

## Сверка менеджером

В Payment review менеджер своей точки видит открытые попытки старше окна фоновой сверки и их `tx_ref`. Панель показывает по 50 попыток, начиная с самой старой брони. Время последней проверки означает начало запроса. Сам результат нужно сверить отдельно.

По действию менеджера сервер запрашивает Flutterwave по сохранённому `tx_ref`. Для таких старых попыток менеджер и покупатель делят интервал в 60 секунд на попытку. Если провайдер не нашёл транзакцию или не подтвердил списание, дело остаётся открытым. Ошибка провайдера или расхождение данных показывается в панели, а попытка остаётся доступной для сверки. Подтверждённый поздний платёж с истёкшей бронью появляется в списке исключений и ждёт проверенного возврата. Возврат оформляется в Flutterwave и сверяется отдельно. [Проверка по tx_ref](https://developer.flutterwave.com/api/transactions/verify-transaction-with-tx-ref)

## Проверки

`./gradlew test --tests 'com.crustcaper.api.payment.*'` из `server/` проверяет обмен JSON, время ожидания, отказ от перенаправления HTTP-клиента, разрешённые checkout URL, корректность суммы и сверку идентификаторов на локальном HTTP-стенде. `FlutterwaveCheckoutIntegrationTest` использует настоящий адаптер, изолированную PostgreSQL и локальный имитатор. Сценарий проверяет потерю ответа после отправки, повтор с тем же ключом, отказ при недостаточном списании, подтверждение через вебхук и один заказ в кухонной очереди.

Из корня репозитория `npm run test:storefront:payment-restart` проверяет фоновое восстановление после принудительной остановки контейнера API. Имитатор провайдера работает отдельно и сохраняет подтверждённую оплату. После перезапуска планировщик Spring повторно сверяет попытку из PostgreSQL, а кухня видит один оплаченный заказ. Подготовка изолированного HTTPS-стенда описана в [инструкции выпуска](../../docs/runbooks/CONNECTED_RELEASE.md#локальный-прогон-https).

Для приёмки на стенде владелец настраивает Flutterwave Test, домен возврата и доставку webhook. На конкретном кандидате проверить успешную и отклонённую оплату, повтор в открытой hosted-странице, отсутствие перенаправления, дубли webhook, оплату у конца брони и сверку суммы в RWF. Формат и фактическое время действия `link_expiration`, доступность карт и Mobile Money Rwanda подтвердить на подключённом мерчанте. [Способы оплаты Flutterwave](https://developer.flutterwave.com/docs/payment-methods)
