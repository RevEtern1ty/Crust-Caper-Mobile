# Резервное копирование и восстановление PostgreSQL

Репетицию выполняйте в отдельной PostgreSQL с закрытым доступом и синтетическими заказами. Зафиксируйте версию выпуска, версию PostgreSQL и назначение окружения. Используйте клиентские утилиты PostgreSQL 17 для сервера 17. Для другой основной версии сначала проверьте совместимость утилит, сервера и архива. Логическая копия сохраняет схему и данные одной БД на момент снимка. Для восстановления на выбранный момент между снимками настройте отдельное резервирование на уровне платформы с журналом WAL. [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) · [Восстановление до момента времени](https://www.postgresql.org/docs/17/continuous-archiving.html)

## Создание копии

Запускайте скрипты из корня репозитория в Bash на выделенном узле с доступом к приватной БД. Для копирования используйте отдельную роль с доступом на чтение прикладных объектов. Для сетевого подключения задайте DNS-имя из сертификата, CA и `PGSSLMODE=verify-full`. Смените параметры в примере на параметры своего окружения. Передайте пароль через закрытый `PGPASSFILE` с режимом `0600` на Linux. Запускайте команды с проверенным набором переменных libpq для нужного окружения. [Файл паролей libpq](https://www.postgresql.org/docs/17/libpq-pgpass.html) · [Проверка TLS](https://www.postgresql.org/docs/17/libpq-ssl.html)

```sh
(
  export PGHOST=db.internal PGPORT=5432 PGDATABASE=crustcaper PGUSER=crustcaper_backup
  export PGSSLMODE=verify-full PGSSLROOTCERT=/etc/crustcaper/db-ca.pem
  export PGPASSFILE=/run/crustcaper/backup.pgpass
  bash server/tooling/backup-postgres.sh "/secure/backup/crustcaper-$(date -u +%Y%m%dT%H%M%SZ).dump"
)
```

Скрипт сохраняет архив с режимом `0600` на файловой системе Linux с поддержкой жёстких ссылок. Итоговое имя появляется после успешного создания копии. Если имя занято, скрипт завершится с ошибкой. При ожидании блокировки дольше десяти секунд `pg_dump` завершится с ошибкой. Сохраните отдельно SHA-256, выведенный скриптом, и запишите время снимка в UTC, версию кандидата и размер. Перед восстановлением используйте эту сохранённую контрольную сумму.

Архив содержит контакты покупателей, коды выдачи, сведения о платежах, хеши учётных данных и файлы чеков. Держите промежуточные файлы в закрытом каталоге на шифрованном носителе. Отправляйте готовые копии в шифрованное хранилище вне узла БД с отдельным доступом на восстановление. Проверяйте целостность после переноса, контролируйте пропуски копирования и регулярно проверяйте восстановление из сохранённого экземпляра. Частоту, срок хранения, шифрование и процедуру удаления утверждает владелец данных.

Роли и пароли уровня PostgreSQL, ключи внешних сервисов, правила доступа и параметры подключения хранятся отдельно. Зафиксируйте их в защищённом реестре развёртывания. Для сохранённых Expo-токенов учитывайте связанный ключ шифрования из серверного хранилища секретов. [Конфигурация push](PICKUP_ALERTS.md)

## Восстановление в новую БД

Проверьте происхождение и контрольную сумму архива перед восстановлением. Архив PostgreSQL содержит команды SQL. Используйте доверенную копию в закрытом каталоге без фоновой синхронизации и других процессов записи. Доступ к ней и ключам выдавайте только участникам восстановления. Подготовьте отдельный закрытый экземпляр PostgreSQL с совместимыми кодировкой, локалью и нужными расширениями. Убедитесь, что к нему пока не обращаются действующие экземпляры API и что репетиция изолирована от Flutterwave, Twilio и Expo. [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)

Задайте прямой адрес одного экземпляра PostgreSQL, служебную БД в `PGDATABASE` и роль, которая может создавать базы и будет владельцем восстановленных объектов. Используйте адрес без балансировщика или автоматического переключения на другой экземпляр. По умолчанию служебная БД называется `postgres`. В `PGPASSFILE` предусмотрите доступ роли к служебной и будущей БД. Для обеих БД используйте имена длиной до 63 символов из строчных латинских букв, цифр и подчёркиваний с буквой или подчёркиванием в начале. Передайте третьим аргументом SHA-256 из сохранённой записи о копии. В примере отдельный файл содержит только этот хеш.

```sh
(
  export PGHOST=recovery-db.internal PGPORT=5432 PGDATABASE=postgres PGUSER=crustcaper_recovery
  export PGSSLMODE=verify-full PGSSLROOTCERT=/etc/crustcaper/recovery-db-ca.pem
  export PGPASSFILE=/run/crustcaper/recovery.pgpass
  export TMPDIR=/secure/recovery
  read -r backup_sha < /secure/metadata/crustcaper.sha256
  bash server/tooling/restore-postgres.sh /secure/recovery/crustcaper.dump crustcaper_recovered "$backup_sha"
)
```

Скрипт проверяет SHA-256 закрытой временной копии и применяет эту копию одной транзакцией в новой БД. Предусмотрите в `TMPDIR` на шифрованном носителе свободное место размером с архив. Если имя БД занято, операция останавливается до загрузки данных. Создание БД выполняется отдельно от транзакции. При ошибке новая БД может остаться на экземпляре. Проверьте её состояние и используйте новое имя для повторного прогона. Схема переносится с владельцем на стороне восстановления. Воссоздайте права и логины для сервиса по утверждённым настройкам экземпляра. Закройте доступ к восстановленной БД для остальных ролей до переключения.

## Приёмка и переключение

1. Прочитайте историю Flyway и подтвердите, что версия приложения и контрольные суммы миграций подходят к копии. Сверьте состояние точки и лимиты окон, количество и состояния заказов, привязку попыток оплаты и возвратов, журнал действий сотрудников и контрольную сумму контрольного PDF. В отчёт вносите обезличенные результаты.
2. На синтетической копии запустите подходящий выпуск API в закрытом контуре и проверьте readiness под штатной ролью приложения. Откройте сохранённый оплаченный заказ гостевой сессией владельца, скачайте его чек и проверьте очередь кухни под учётной записью сотрудника. Оформите новый синтетический заказ и убедитесь, что он сохраняется и появляется у оператора после оплаты. До переключения проверяйте копию реальных данных запросами на чтение и сверяйте выданные права.
3. Перед переключением после сбоя остановите приём заказов и обработчики старого контура. Сверьте платежи и возвраты с момента снимка по исходным ссылкам транзакций во Flutterwave. Начинайте с выписки провайдера за интервал после снимка и сопоставляйте каждый результат с восстановленной попыткой. Если у подтверждённого списания нет заказа в копии, передайте случай владельцу сверки и оставьте приём на паузе до согласованного решения. Перед списанием, выдачей или формированием чека подтвердите состояние исходной операции. Сверьте выдачи с точкой, фискальные документы с EBM и незавершённые уведомления с состоянием доставки. [Платёжный контур](PAYMENTS.md) · [Проверка возвратов и документов](OPERATIONS.md)
4. По журналу учётных записей и обращений повторите отключения, отзывы сеансов и удаления данных, выполненные после снимка. Если журнал за этот интервал неполон, отзовите затронутые сеансы и потребуйте повторный вход до переключения. Возвращайте ключи шифрования только для восстановленных данных, на которые действуют права хранения.
5. После проверки прав и согласования расхождений укажите проверенную БД в настройках API, повторите readiness, контрольный заказ и проверку очереди. Возобновляйте обслуживание и внешние обработчики по согласованному плану. Зафиксируйте время снимка, интервал потерянных записей, время от начала восстановления до готовности API и результат тестов. Сравните измерения с утверждёнными RPO и RTO перед допуском трафика.

## Репетиция с заказами

Запустите `npm run test:storefront:database-recovery` по инструкции связанного выпуска. Команда создаёт одноразовый HTTPS-контур с логическим восстановлением в новую БД на изолированном экземпляре PostgreSQL. API оформляет настоящие записи тестовых заказов и принимает оплату от синтетического провайдера. Провайдер работает отдельным процессом и сохраняет свой реестр при переключении API.

Контрольный набор включает оплаченный заказ с прикреплённым PDF, незавершённую оплату в снимке, подтверждённое провайдером списание по заказу, созданному после снимка, и новый контрольный заказ после восстановления. Проверьте доступ владельца к старому заказу и чеку, очередь кухни, неизменный идентификатор восстановленной платёжной попытки и отсутствие второго списания при повторе. Случай с оплатой после снимка остаётся расхождением для отдельной сверки. После упражнения сохраните обезличенный отчёт с границами снимка, временем до readiness и временем до контрольной покупки. На целевом хосте повторите измерения с утверждённым объёмом данных, расписанием копирования и хранилищем WAL.
