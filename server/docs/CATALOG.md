# Загрузка каталога точки

Оператор загружает утверждённые сведения о точке, меню и окнах самовывоза после применения миграций Flyway. Импорт проверяет входные данные и выполняется в одной транзакции PostgreSQL. По умолчанию выполняется пробный прогон с откатом.

## Подготовка данных

Возьмите [пример JSON](../tooling/catalog.example.json) и замените адрес, часы, налог, состав, аллергены, цены, доступность и даты окна утверждёнными значениями. Для первого импорта используйте `expectedVersion: null`. Для обновления прочитайте `version` текущего каталога, передайте её в `expectedVersion` и задайте новую `store.version`.

| Поле | Правило |
| --- | --- |
| `store` | Идентификатор совпадает с точкой клиента, например `kigali`. Он начинается с латинской буквы или цифры и содержит до 64 символов из латинских букв, цифр, точек, дефисов и подчёркиваний. Название, адрес и часы содержат `en` и `rw`. `open` управляет приёмом заказов. |
| `taxBasisPoints` | Ставка налога в базисных пунктах. Пример `1800` означает 18%. Цены каталога включают налог. Подставьте утверждённую ставку. |
| `products` | Для каждой позиции укажите SKU, категорию, описание, состав, аллергены, цену в целых RWF, доступность и модификаторы. `available: false` помещает позицию в стоп-лист. Порядок записей задаёт порядок этих позиций. Для полного изменения порядка включите все позиции. |
| `slots` | Каждое окно имеет ID, `startsAt` и `endsAt` с часовым смещением или UTC, а также целочисленную `capacity`. Для переноса занятого окна заведите новый ID. |
| `supportUrl`, `directionsUrl`, `photoUrl` | Допускаются публичные HTTPS-ссылки на стандартном порту 443. Для каталога с веб-заказом используйте фото на домене витрины по инструкции ниже. Оставьте отсутствующее поле вне JSON. |

Импорт добавляет и обновляет явно перечисленные строки. Пустой список оставляет соответствующие товары или слоты без изменений. Для снятия товара с продажи передайте его с `available: false`. Для прекращения новых заказов на всю точку укажите `store.open: false`. Чтобы закрыть одно незанятое окно, установите `capacity: 0`. Для занятого окна можно установить квоту равной числу занятых мест. Подтверждённые заказы и действующие брони сохраняются. При открытии нового окна сохраните прежний ID и время для уже принятых заказов.

## Пробный прогон и запись

Настройте PostgreSQL service для конкретного окружения и проверьте, что он указывает на целевой сервер. Роли импортёра нужны `SELECT`, `INSERT` и `UPDATE` на `stores`, `menu_products` и `pickup_slots`, право создавать временные таблицы и чтение столбцов `store_id`, `slot_id`, `status` и `reservation_expires_at` в `orders`. Имя в `catalog_database` должно совпасть с именем базы в подключении. Для удалённого PostgreSQL задайте TLS с проверкой имени сервера в service и используйте штатное защищённое хранилище реквизитов.

Из корня репозитория в PowerShell загрузите UTF-8 файл. Сначала выполните пробный прогон.

```powershell
$catalogDatabase = 'crustcaper_stage'
$catalogFile = (Resolve-Path -LiteralPath '.\approved-catalog.json').Path
$catalogInput = [Convert]::ToBase64String([System.IO.File]::ReadAllBytes($catalogFile))
$catalogInput | psql -X --no-password --dbname='service=crustcaper-stage' -v "catalog_database=$catalogDatabase" -f server/tooling/import-catalog.psql
```

Проверьте целевую точку, новую версию и количество переданных записей в выводе. Для записи того же файла выполните команду с `-v catalog_apply=true`.

```powershell
$catalogInput | psql -X --no-password --dbname='service=crustcaper-stage' -v "catalog_database=$catalogDatabase" -v catalog_apply=true -f server/tooling/import-catalog.psql
```

Для входа через другую оболочку передайте в stdin одну строку Base64 исходного файла. `psql` читает эту строку через `\copy ... FROM PSTDIN`. [Документация PostgreSQL](https://www.postgresql.org/docs/17/app-psql.html)

При конфликте версии прочтите текущий каталог, сверьте изменения и заново выполните пробный прогон. Новые и перенесённые окна проверяются на пересечение со всем расписанием точки, включая окна из панели менеджера. Для отката подготовьте предыдущие значения с текущей `expectedVersion` и новой `version`. Ограничения для занятых окон применяются и при откате.

## Публикация фотографий

Для веб-витрины положите утверждённые фотографии в отдельный каталог, доступный Caddy на чтение. Используйте обычные файлы без вложенных каталогов и символических ссылок. Имя без расширения начинается с латинской буквы в нижнем регистре или цифры и содержит до 120 строчных латинских букв, цифр, точек, дефисов и подчёркиваний. Поддерживаются расширения `.avif`, `.jpg`, `.jpeg`, `.png` и `.webp`.

Задайте `CRUSTCAPER_CATALOG_PHOTOS_DIR` с абсолютным путём в файле переменных Compose. Подключите `-f server/deploy/compose.catalog-photos.yml` после файлов [развёртывания каталога](../README.md#public-menu) и запустите проверку конфигурации и обновление того же проекта. Caddy отдаёт фото из этого каталога по `/catalog-photos/`. Значение `photoUrl` в утверждённом каталоге выглядит как `https://stage.example.com/catalog-photos/double-smash-v1.jpg`. При замене фото используйте новое имя файла и обновите `photoUrl` при импорте следующей версии каталога.

## Проверка перед приёмом заказов

После импорта и открытия точки из корня репозитория запустите команду с Node.js 24. Передайте HTTPS-адрес API и ожидаемые `store.id` и `store.version` из утверждённого файла.

```sh
node server/tooling/check-live-catalog.mjs https://stage.example.com/api/v1 kigali catalog-001
```

Проверка читает общедоступное меню без авторизации. Команда успешна, если точка и версия совпадают, приём заказов открыт, доступно хотя бы одно блюдо и есть будущее свободное окно. Запрос имеет таймаут 8 секунд. Для локальной проверки допустим HTTP на `127.0.0.1` или `[::1]`. Цены, состав и аллергены сверяются отдельно с утверждённым каталогом.

Для веб-витрины добавьте `--storefront` после версии каталога. Команда проверит обе публичные страницы `/menu/en` и `/menu/rw` через тот же домен. Они должны отдавать меню ожидаемой точки и версии. Для каждого указанного `photoUrl` проверяются прямой ответ с изображением, тип файла и признаки неполной загрузки. Проверка читает до 8 МиБ на изображение с таймаутом 8 секунд на запрос. Откройте обе языковые страницы и визуально сверьте утверждённые фотографии до открытия заказов для гостей.

Для допуска веб-заказов используйте `--checkout`. Команда выполняет проверки витрины, находит ссылку на одну доступную позицию в каждой локали и проверяет переход со страницы блюда в оформление с тем же языком. На HTTPS-домене проверяются HTML Expo и загружаемый JS-файл. Проверка сверяет байты файла с хешем в его имени, синтаксис JS и опубликованные настройки веб-оформления для этой точки и домена. Лимит составляет 1 МиБ для HTML оформления и 12 МиБ для JS, таймаут 8 секунд на запрос. Проверка использует только GET и не выполняет код клиента. Отдельно пройдите браузерный сценарий до оплаты и проверьте заказ в очереди кухни.

```sh
node server/tooling/check-live-catalog.mjs https://stage.example.com/api/v1 kigali catalog-001 --checkout
```

## Управление в течение смены

Менеджер открывает **Menu availability** в операторской панели. **Pause new orders** закрывает приём новых заказов для точки. **Put on stop list** прекращает продажу одной позиции. После проверки наличия менеджер возобновляет продажу позиции или приём заказов соответствующей кнопкой.

Каждое фактическое изменение получает новую версию каталога и именную запись. При конфликте версий обновите экран и проверьте текущие значения перед повтором. Импортёр использует ту же версию. Перед импортом сверьте активные ограничения и перенесите нужные значения в файл либо исключите изменяемую позицию из обновления. Приём на кухне, оплата и выдача оформленных заказов следуют их существующим бронированиям.

### Лимиты самовывоза

В **Pickup limits** менеджер выбирает одно из ближайших 36 будущих окон, видит текущий лимит и занятые места и сохраняет новое значение. Ноль закрывает пустое окно. Если уже есть оплаченные заказы или действующие брони, сервер принимает лимит от числа занятых мест. Если окно заполнено, клиент видит его недоступным и может выбрать другое. При увеличении лимита свободные места снова доступны для бронирования.

`PATCH /api/v1/operator/availability` принимает `{expectedVersion,slotId,capacity}`. Сервер сверяет точку и версию каталога, блокирует строку окна и пересчитывает действующие брони. Последнее место может быть занято после открытия панели. В этом случае попытка снижения ниже фактической занятости возвращает `409 slot_capacity_below_reserved`, а для начавшегося окна используется `409 slot_update_closed`. После конфликта менеджер сверяет актуальные значения перед новой попыткой. [Блокировки строк PostgreSQL](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS)

Изменение лимита добавляет в аудит старое и новое значение, версию и учётную запись менеджера. При повторе с текущей версией и сохранённым значением новой записи нет.

### Публикация окон самовывоза

В **Menu availability** менеджер может опубликовать окна на выбранную дату по времени Кигали. Укажите начало, конец и число заказов на каждое десятиминутное окно. Проверьте дату, часы и количество окон перед подтверждением. Начало первого окна должно быть в будущем. Время окончания задаёт границу последнего окна.

Публикация добавляет окна только для точки менеджера, меняет версию каталога и сохраняет именную запись. При пересечении с существующим расписанием сервер отклоняет весь диапазон. Границы соседних окон могут совпадать. Во время паузы новые окна станут доступны покупателям после возобновления приёма заказов.

При неопределённом ответе используйте повтор той же публикации из панели. Для одной операции используется тот же идентификатор и параметры. Если она уже сохранена, API возвращает свежий снимок каталога. Если версия изменилась до публикации, обновите панель и заново сверьте расписание перед подтверждением. В панели лимитов доступны ближайшие 36 окон, покупателям показываются ближайшие 12.
