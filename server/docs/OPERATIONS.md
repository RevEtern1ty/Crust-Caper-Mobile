# Работа кухни и выдачи CrustCaper

Веб-интерфейс доступен по `/operator/index.html` на том же HTTPS-адресе, что и API. Сотрудник входит под своей учётной записью. Очередь показывает оплаченные прямые заказы и зарегистрированные вручную заказы площадок доставки его точки со статусами `accepted`, `preparing` и `ready`. Для прямых заказов передаются SKU, идентификаторы добавок и количество.

| Роль | Действия |
| --- | --- |
| `kitchen` | Начать приготовление и отметить готовность. |
| `pickup` | Выдать прямой заказ по коду покупателя, зарегистрировать заказ площадки и передать его по внешнему номеру. |
| `manager` | Выполнить любой из этих переходов и отменить активный заказ. |

Статусы идут по порядку `accepted` → `preparing` → `ready` → `collected`. Сервер проверяет точку, роль, состояние и код под блокировкой строки заказа. При выдаче он удаляет код и записывает переход с именованным сотрудником, временем и точкой в той же транзакции. После пяти ошибочных кодов сотрудник ждёт до двух минут перед новой попыткой для этого заказа. В журнал ошибки попадает факт несовпадения без введённого кода.

## API и сессия

- `POST /api/v1/operator/sessions` принимает `{username,password,authenticatorCode}` и возвращает `201 {accessToken,expiresAt,storeId,role}`. Код состоит из шести цифр и передаётся строкой. Bearer действует один час. Пять последовательных неудачных попыток ограничивают вход на две минуты. У синтетических сотрудников локального стенда поле кода можно оставить пустым.
- `GET /api/v1/operator/orders` с `Authorization: Bearer …` возвращает `{serverTime,orders:[{id,status,paymentStatus,lines,pickupStartsAt,pickupEndsAt,acceptedAt}]}`. При наличии активных заказов площадок сервер добавляет `externalOrders`. Телефон, email, суммы, чеки и код выдачи не выдаются.
- `POST /api/v1/operator/orders/{id}/status` с bearer принимает `{status,pickupCode?}` и возвращает обновлённый заказ в том же формате. Код требуется для `collected`. При обновлении из устаревшей карточки сервер возвращает `409 invalid_transition`. Для действующей карточки с неверным кодом ответ `409 pickup_code_mismatch`.
- `POST /api/v1/operator/orders/{id}/cancel` с bearer менеджера отменяет оплаченный заказ его точки на стадиях `accepted`, `preparing` и `ready`. Повтор возвращает актуальное состояние уже отменённого рестораном заказа. Ответ `409 payment_reference_unavailable` означает, что исходную транзакцию требуется сначала сверить.
- `DELETE /api/v1/operator/sessions/current` с bearer отзывает эту сессию. Ответ `204`.

Пароли хранятся в виде PBKDF2-HMAC-SHA-256 с 600 000 итераций и собственной случайной солью. В PostgreSQL записывается SHA-256 случайного bearer. Ответы операторского API помечены `no-store`. Не включайте тела входа и выдачи или заголовки авторизации в прокси-логи. Для публичного HTTPS-адреса настройте ограничение частоты входа на границе, прежде чем открыть операторский экран персоналу. [Хранение паролей OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [Управление сессиями OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet)

## Сигналы кухни

На открытой панели кухни и менеджера **New paid orders** показывает число оплаченных заказов, по которым ещё требуется нажать **Start preparing**. Надпись **Check this order** появляется после минуты ожидания. Для расчёта времени используются часы базы и `acceptedAt`, установленный в транзакции подтверждения оплаты. Заказ, созданный до этой миграции, остаётся в счётчике и очереди. Возраст для него не рассчитывается.

Чтобы получать звук, сотрудник включает **Enable order sound** после входа. Сигнал повторяется примерно раз в 20 секунд, пока в актуальной очереди есть заказы в ожидании приготовления. Кнопка **Mute order sound** оставляет визуальный сигнал. Звук работает в открытой вкладке при подтверждённой связи с сервером. [Правила Web Audio в Chrome](https://developer.chrome.com/blog/autoplay/#web-audio)

При сбое панель помечает последнюю очередь как устаревшую и приостанавливает переходы кухни до чтения актуального состояния. После восстановления соединения она запрашивает очередь заново. Для пилота измерьте время от подтверждения тестового платежа до появления заказа в панели на рабочем устройстве. Ориентир плана — до 10 секунд при рабочей сети. Затем проверьте повтор сигнала, отключение звука, потерю связи и начало приготовления на второй панели.

Сообщение **No paid orders are waiting** показывается после успешного чтения пустой очереди. При сбое уже загруженные карточки остаются видимыми с отметкой об устаревании. Если панель показывает **Support ID**, сотрудник передаёт этот идентификатор и время сбоя. Для обработанных серверных ошибок найдите `requestId` в событиях `api_request_failed`. Запись содержит шаблон маршрута, метод, статус, категорию и время обработки в миллисекундах. Если события нет, проверьте журнал API и контейнера за это время. При ошибке без идентификатора также проверьте журнал Caddy, доступность API и БД.

В конфигурации из инструкции развёртывания выполните `stage_compose logs --tail 200 api`. Событие исключает URL запроса, его тело, данные авторизации и текст исключения. [Запуск HTTPS-стенда](../README.md#single-host-https-staging)

## Заказы площадок доставки

Администратор ресторана включает только площадки, с которыми у точки заключено соглашение. После применения Flyway администратор базы добавляет согласованные идентификатор канала и название в `operator_external_order_channels`. У одной точки может быть несколько площадок. ID состоит из строчных латинских букв, цифр, дефисов, точек или подчёркиваний. Отключённый канал скрывается из формы, а уже принятые заказы остаются в очереди до завершения.

```sql
INSERT INTO operator_external_order_channels (store_id, id, label, enabled)
VALUES (:'store_id', :'channel_id', :'channel_label', true)
ON CONFLICT (store_id, id) DO UPDATE
SET label = excluded.label, enabled = excluded.enabled;
```

Сотрудник выдачи или менеджер открывает **Add delivery order**, выбирает площадку, указывает внешний номер, время передачи по Кигали, позиции, количество и добавки. Номер переносится полностью, включая регистр и начальные нули. Вводите только состав для кухни и внешний номер. Контакт покупателя и адрес остаются в системе площадки.

Запись сразу появляется у кухни рядом с прямыми заказами. Кухня отмечает приготовление и готовность. При передаче курьеру сотрудник выдачи сверяет площадку и вводит внешний номер из подтверждения передачи. Менеджер может закрыть отменённый заказ до передачи. Дальнейшее оформление отмены, оплаты, чека и расчётов ведётся в согласованной системе площадки. Заказ площадки не занимает бронь прямого самовывоза.

Если ответ на регистрацию потерялся, повторите сохранение с теми же данными. Сервер возвращает прежний заказ даже после передачи или выключения площадки. Если по тому же сочетанию точки, площадки и номера уже есть заказ с другим составом или временем, сервер возвращает конфликт. Перед новым вводом найдите его в исходной системе и проверьте очередь, чтобы кухня не получила второй экземпляр.

## Отмена до выдачи

Если ресторан не может выполнить заказ, менеджер выбирает **Cancel order** на его карточке, сверяет номер и подтверждает действие. Сервер убирает заказ из рабочей очереди, освобождает место в окне выдачи, удаляет код выдачи и останавливает ещё не отправленное уведомление о готовности. В журнале сохраняются предыдущий статус, время и учётная запись менеджера.

Покупатель видит `cancelled` и `refund_pending`. Исходная транзакция появляется в **Payment review** с причиной **Restaurant cancelled**. Менеджер оформляет полный возврат в Flutterwave и сверяет его по этой записи. При необходимости продавец оформляет корректировку в EBM по своему регламенту. [Возвраты Flutterwave](https://developer.flutterwave.com/docs/payment-operations/refunds)

## Проверка платежей

В разделе **Payment review** менеджер своей точки начинает с открытых исключений. Старые операции отображаются первыми. Проверенные возвраты доступны в истории. Панель загружает до 50 строк за запрос. Если записей больше, загрузите следующую страницу.

`GET /api/v1/operator/payment-exceptions?state=open` выдаёт открытые исключения, а `state=verified` — историю от новых записей к старым. Для продолжения передайте `nextCursor` из предыдущей страницы в параметре `after` с тем же состоянием. Сервер определяет сверку по записи о возврате конкретного списания. Поэтому сверка одного списания оставляет остальные исключения по заказу в очереди до их обработки. Старый запрос без параметров выдаёт 50 последних записей. Сервер проверяет роль `manager` и точку для просмотра и записи.

В панели Flutterwave найдите транзакцию по `providerTransactionId` и сверьте её с `merchantReference`. После завершения полного возврата в кабинете Flutterwave введите его идентификатор в **Payment review** и нажмите **Verify refund**. Spring запрашивает результат у провайдера, сверяет транзакцию, сумму, валюту и завершённое состояние, затем сохраняет проверку с именем менеджера. После подтверждения панель переносит операцию в историю. При потере ответа повторите проверку с тем же идентификатором возврата. После сверки возврата исходной оплаты по отменённому заказу покупатель увидит `refunded`. [Возвраты Flutterwave](https://developer.flutterwave.com/docs/payment-operations/refunds)

## Фискальные чеки

Фискальный оригинал оформляется в EBM фискального продавца. В разделе **Fiscal receipts** менеджер своей точки находит оплаченный заказ, сверяет оплаченную сумму, вводит номер с документа и прикрепляет исходный PDF размером до 1 МиБ. В очереди видны оплаченные заказы до и после выдачи, заявки без прикреплённого чека находятся в начале. [Системы EBM и подключение RRA](https://www.rra.gov.rw/en/ebm-electronic-billing-machine/request-and-install-ebm)

Сервер сверяет введённую сумму с оплаченным заказом в RWF, сохраняет файл, уникальный номер чека и запись менеджера. Покупатель получает файл через авторизованный экран заказа. Тот же доступ есть у гостя, который подтвердил телефон для этого заказа. Исправления и возвратные документы ведутся в EBM. Перед запуском точки проверьте выпуск оригинала, правила исправлений и согласованный срок хранения. [Инструкция подключённого выпуска](../../docs/runbooks/CONNECTED_RELEASE.md)

## Ежедневная сверка

Менеджер открывает **Daily reconciliation**, выбирает дату по Кигали и загружает CSV для сверки своей точки. Суммы в RWF берутся из записей CrustCaper. Сопоставьте строки с журналом кассы и EBM, транзакциями Flutterwave и выпиской по банку. Комиссии и фактические перечисления сверяйте по выпискам провайдера и банка.

| Строка отчёта | Дата и сумма |
| --- | --- |
| Принятый заказ | Сумма заказа и момент приёма после подтверждения оплаты. Последующая отмена или возврат отражается отдельной операцией. |
| Платёжное исключение | Сумма и дата записи конкретного позднего, повторного или заменённого списания. Сверка одного списания меняет состояние только его строки. |
| Отмена рестораном | Дата регистрации отмены. Сумма относится к исходному списанию и учитывается в его строке оплаты. |
| Проверенный возврат | Сумма и дата, когда менеджер подтвердил возврат в CrustCaper. |
| Прикреплённый чек | Сумма чека и дата его добавления в CrustCaper. Дату выдачи сверяйте с оригиналом из EBM. |

Неприкреплённые чеки в сводке относятся к принятым заказам выбранного дня, которые остаются оплаченными на момент просмотра. Открытые платёжные исключения этого дня считаются по состоянию на тот же момент. Если у старых принятых заказов отсутствует достоверная дата, их количество и сумма видны отдельно от разбивки по дням.

Используйте полный идентификатор заказа и идентификаторы платёжной попытки и транзакции при сопоставлении строк. Если платёжную попытку нельзя связать однозначно, её поля в строке остаются пустыми. При импорте CSV задайте текстовый тип для идентификаторов транзакций и возвратов, чтобы сохранить все цифры.

## Выдача доступа

На локальном сервере с `SPRING_PROFILES_ACTIVE=local` и провайдером `local` создаются синтетические сотрудники `demo-kitchen`, `demo-pickup` и `demo-manager` для тестовой точки. Пароль каждой локальной записи `local-demo-passphrase`. Префикс `demo-` зарезервирован для этих записей. Их пароли и сессии отвергаются вне локального режима даже при наличии строк в базе.

Для подключённой точки администратор БД создаёт отдельную учётную запись для каждого сотрудника. Сгенерируйте пароль и передайте его сотруднику по защищённому каналу. Генератор считывает пароль без отображения и выводит хеш. Из каталога `server/` после компиляции Java запустите его в интерактивном терминале.

```sh
java -cp build/classes/java/main com.crustcaper.api.operator.OperatorPasswordHash
```

Для собранного серверного JAR используйте тот же генератор через штатный загрузчик Spring Boot.

```sh
java -Dloader.main=com.crustcaper.api.operator.OperatorPasswordHash -cp crustcaper-api.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

Запустите [инструмент управления доступом](../tooling/operator-accounts.psql) через `psql` на выделенном подключении администратора. Для окружения настройте PostgreSQL service с проверкой имени сервера и утверждённым CA. Сверьте точку и точное имя базы. Введите хеш в приглашении PowerShell, чтобы сохранить его вне аргументов командной строки и истории оболочки. Пример выполняется из корня репозитория.

```powershell
$operatorDatabase = 'crustcaper_stage'
$operatorAccount = @{
    operation = 'create'
    storeId = 'kigali'
    accountId = [Guid]::NewGuid().ToString()
    username = 'staff-example'
    role = 'kitchen'
    passwordHash = Read-Host 'Paste the generated password hash' -MaskInput
}
try {
    $operatorAccount | ConvertTo-Json -Compress | ForEach-Object {
        [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($_))
    } | psql -X --no-password --dbname='service=crustcaper-stage' -v "operator_database=$operatorDatabase" -f server/tooling/operator-accounts.psql
} finally {
    $operatorAccount.Remove('passwordHash')
}
```

Сохраните идентификатор сотрудника из результата в реестре доступа. Для смены пароля передайте `operation = 'rotate'`, тот же `storeId`, `accountId` и `username`, а также новый хеш без поля `role`. Смена пароля сбрасывает блокировку входа и отзывает все сессии в одной транзакции. Для прекращения доступа используйте `operation = 'disable'` и три поля идентификации. Отключённая учётная запись остаётся в истории действий. Повтор точной смены пароля и повтор отключения безопасны.

Используйте один и тот же UUID после неопределённого результата создания. Если инструмент сообщает о существующей записи, сверьте сотрудника и точку в реестре. Вывод инструмента содержит результат операции и число отозванных сессий. Хеш при передаче через stdin требует той же защиты, что и другие секреты.

### Аутентификатор сотрудника

На подключённом стенде и в production для каждой записи обязательны пароль и код аутентификатора. Установите `CRUSTCAPER_OPERATOR_MFA_KEY` из хранилища секретов целевого окружения. Это отдельный ключ из 32 случайных байтов в Base64. Для восстановления базы храните резервную копию ключа в хранилище секретов. Прежние сессии, выданные только по паролю, при обновлении требуют нового входа.

После создания записи запустите генератор в интерактивном терминале с ключом этого же окружения. Он запрашивает точку, UUID и имя сотрудника. Добавьте выданный Base32-ключ в приложение-аутентификатор сотрудника с шестью цифрами и интервалом 30 секунд. Подтвердите текущий код в генераторе. Передавайте ключ аутентификатора сотруднику лично или по защищённому каналу. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)

```sh
java -cp build/classes/java/main com.crustcaper.api.operator.OperatorTotpEnrollment
```

Для готового JAR запустите тот же генератор через Spring Boot.

```sh
java -Dloader.main=com.crustcaper.api.operator.OperatorTotpEnrollment -cp crustcaper-api.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

Передайте выданную генератором строку с зашифрованной записью через stdin в уже настроенное административное подключение. Ввод действителен для UUID, точки и имени, указанных при генерации.

```powershell
$operatorDatabase = 'crustcaper_stage'
$enrollment = Read-Host 'Paste the encrypted enrollment payload' -MaskInput
try {
    $enrollment | psql -X --no-password --dbname='service=crustcaper-stage' -v "operator_database=$operatorDatabase" -f server/tooling/operator-accounts.psql
} finally {
    Remove-Variable enrollment
}
```

При утрате устройства администратор подтверждает личность сотрудника, выпускает новую привязку и применяет её к тому же UUID. Замена отзывает текущие сессии. Повтор уже применённого запроса оставляет действующую привязку и сессии в прежнем состоянии. Проверьте новый вход сразу после применения. Если для генератора использовался ключ другого окружения, выпустите новую привязку с ключом целевого сервера. При прекращении доступа отключите запись. Синхронизируйте часы сервера и телефона. После успешной авторизации дождитесь следующего кода для повторного входа.

## Проверка контура

Из `server/` запустите локальный PostgreSQL через `docker compose -f compose.local.yml up -d --wait`, затем выполните `./gradlew test --tests 'com.crustcaper.api.operator.*'`. Проверка создаёт изолированные тестовые точки, проходит от гостевого заказа до выдачи и проверяет конкуренцию, ограничения доступа и отсутствие приватных полей в операторском API. [Параметры локальной БД](../compose.local.yml)

На подключённом стенде назначьте реальные роли сотрудникам двух тестовых точек. Проверьте изоляцию очередей, работу после выхода и просрочки сессии, получение кода только покупателем и единственную выдачу при одновременном запросе. Сверьте историю с участником и конкретным SHA сборки.
