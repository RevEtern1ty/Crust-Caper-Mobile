# Работа кухни и выдачи CrustCaper

Веб-интерфейс доступен по `/operator/index.html` на том же HTTPS-адресе, что и API. Сотрудник входит под своей учётной записью. Очередь показывает оплаченные прямые заказы и зарегистрированные вручную заказы площадок доставки его точки со статусами `accepted`, `preparing` и `ready`. Для прямых заказов передаются SKU, идентификаторы добавок и количество.

| Роль | Действия |
| --- | --- |
| `kitchen` | Начать приготовление и отметить готовность. |
| `pickup` | Выдать прямой заказ по коду покупателя, зарегистрировать заказ площадки и передать его по внешнему номеру. |
| `manager` | Выполнить любой из этих переходов и отменить активный заказ. |

Статусы идут по порядку `accepted` → `preparing` → `ready` → `collected`. Сервер проверяет точку, роль, состояние и код под блокировкой строки заказа. При выдаче он удаляет код и записывает переход с именованным сотрудником, временем и точкой в той же транзакции. После пяти ошибочных кодов сотрудник ждёт до двух минут перед новой попыткой для этого заказа. В журнал ошибки попадает факт несовпадения без введённого кода.

## Поиск заказа у стойки

Если телефон покупателя недоступен, сотрудник выдачи или менеджер просит известный покупателю номер заказа. В панели сотрудник вводит восьмизначный номер или полный ID заказа и сверяет статус и окно самовывоза своей точки. Если короткий номер совпал, найдите полный ID заказа. Для передачи блюда покупатель предъявляет шестизначный код выдачи. Если код недоступен, оставьте заказ открытым и привлеките менеджера к дальнейшей проверке по правилам точки.

## API и сессия

- `POST /api/v1/operator/sessions` принимает `{username,password,authenticatorCode}` и возвращает `201 {accessToken,expiresAt,storeId,role}`. Код состоит из шести цифр и передаётся строкой. Bearer действует один час. Пять последовательных неудачных попыток ограничивают вход на две минуты. У синтетических сотрудников локального стенда поле кода можно оставить пустым.
- `GET /api/v1/operator/orders` с `Authorization: Bearer …` возвращает `{serverTime,orders:[{id,status,paymentStatus,lines,total,currency,pickupStartsAt,pickupEndsAt,acceptedAt}]}`. В карточке прямого заказа отображается сохранённая сумма заказа в RWF. Для заказов площадок сохраняется их внешний номер. Телефон, email, чек и код выдачи исключены из ответа.
- `POST /api/v1/operator/orders/{id}/status` с bearer принимает `{status,pickupCode?}` и возвращает обновлённый заказ в том же формате. Код требуется для `collected`. При обновлении из устаревшей карточки сервер возвращает `409 invalid_transition`. Для действующей карточки с неверным кодом ответ `409 pickup_code_mismatch`.
- `POST /api/v1/operator/orders/{id}/cancel` с bearer менеджера отменяет оплаченный заказ его точки на стадиях `accepted`, `preparing` и `ready`. Повтор возвращает актуальное состояние уже отменённого рестораном заказа. Ответ `409 payment_reference_unavailable` означает, что исходную транзакцию требуется сначала сверить.
- `DELETE /api/v1/operator/sessions/current` с bearer отзывает эту сессию. Ответ `204`.

Пароли хранятся в виде PBKDF2-HMAC-SHA-256 с 600 000 итераций и собственной случайной солью. В PostgreSQL записывается SHA-256 случайного bearer. Ответы операторского API помечены `no-store`. Не включайте тела входа и выдачи или заголовки авторизации в прокси-логи. Для публичного HTTPS-адреса настройте ограничение частоты входа на границе, прежде чем открыть операторский экран персоналу. [Хранение паролей OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) · [Управление сессиями OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet)

## Лимиты оформления

API ограничивает новые котировки и брони по гостевой сессии и по точке в каждом минутном окне UTC. Сайт и приложение используют общий лимит точки. Счётчики хранятся в PostgreSQL и меняются в транзакции оформления. Точный повтор созданной брони возвращает тот же заказ. Оплата и чтение заказов работают через свои маршруты. При исчерпанном лимите API возвращает `429 rate_limited` и время ожидания в секундах в `Retry-After`.

| Переменная API | Значение по умолчанию в минуту |
| --- | --- |
| `CRUSTCAPER_CHECKOUT_QUOTES_PER_SESSION` | 30 новых котировок на сессию |
| `CRUSTCAPER_CHECKOUT_QUOTES_PER_STORE` | 240 новых котировок на точку |
| `CRUSTCAPER_CHECKOUT_ORDERS_PER_SESSION` | 8 новых броней на сессию |
| `CRUSTCAPER_CHECKOUT_ORDERS_PER_STORE` | 120 новых броней на точку |

Изменения применяйте ко всем экземплярам API одной среды. Перед пилотом сверьте пределы с нагрузочным прогоном и утверждённым трафиком точки.

## Сетевые лимиты

В односерверной HTTPS-поставке Caddy передаёт адрес своего непосредственного соединения и подтверждает источник служебным секретом. API игнорирует присланные клиентом данные о сетевом адресе. Сайт и приложение используют общий лимит для каждого внешнего IPv4-адреса или префикса IPv6 `/64`.

| Переменная API | Значение по умолчанию в минуту |
| --- | --- |
| `CRUSTCAPER_EDGE_RATE_SESSIONS_PER_MINUTE` | 120 запросов на гостевую сессию и обновление токена |
| `CRUSTCAPER_EDGE_RATE_OTP_STARTS_PER_MINUTE` | 30 запросов запуска подтверждения телефона, включая восстановление оформления |
| `CRUSTCAPER_EDGE_RATE_OTP_VERIFICATIONS_PER_MINUTE` | 60 проверок кода |
| `CRUSTCAPER_EDGE_RATE_STAFF_LOGINS_PER_MINUTE` | 30 попыток входа сотрудников |
| `CRUSTCAPER_EDGE_RATE_QUOTES_PER_MINUTE` | 120 запросов на котировку |
| `CRUSTCAPER_EDGE_RATE_ORDERS_PER_MINUTE` | 60 запросов на новую бронь |

API держит ограниченное число счётчиков в памяти. Границы минутных окон отсчитываются от запуска API по монотонным часам. Исходные IP не записываются в БД и журнал. При перезапуске счётчики очищаются. На превышение API отвечает `429 rate_limited` и сообщает задержку в `Retry-After`. Точный повтор принятого заказа возвращает исходный заказ. Чтение меню и заказов, уведомления Flutterwave и повторы оплаты проходят по своим маршрутам.

Проверьте лимиты на целевом домене с двух независимых подключений, включая общий Wi‑Fi точки и мобильную сеть. Для другого публичного прокси или нескольких экземпляров API применяйте общий лимит на публичном входе и ограничьте доступ к источнику. [Настройка HTTPS-поставки](../README.md#single-host-https-staging)

## Проверка доступности снаружи

Запустите проверку с узла, который открывает тот же HTTPS-домен, что и покупатели. Подставьте домен пилота и идентификатор точки. Node.js 24 проверяет публичное меню API, страницы EN/RW, форму входа персонала и ответ защищённой очереди на запрос без сессии.

```sh
npm run monitor:storefront -- https://stage.example.com/api/v1 kigali
npm run monitor:storefront -- https://stage.example.com/api/v1 kigali --watch
```

Разовая проверка выводит JSON. Код выхода `0` означает успешные проверки, `1` указывает на сбой, `2` указывает на неверные параметры. В режиме наблюдения следующая проверка начинается через десять секунд после завершения текущей. `ready` означает готовность, `incident` появляется после двух неудачных проверок подряд, `recovered` после двух успешных проверок подряд. Плановая пауза заказов отражается флагом `orderingOpen` и сохраняет нормальную доступность меню.

Направьте строки JSON в журнал эксплуатационной системы. Для оповещений назначьте получателя событий `incident` и `recovered`. Если сбой затронул только `menu_en` и `menu_rw`, проверяйте сервер каталога и HTTPS-прокси. Если одновременно пропал `menu_api`, проверьте доступность API и PostgreSQL. Для ошибок `operator_shell` или `operator_auth` проверьте маршруты панели и статус API. Проверка использует публичные GET-запросы и фиксированные диагностические поля.

При восстановлении подтвердите, что монитор сообщил `recovered`, меню снова открывается, а сотрудник видит актуальную очередь. Сверьте платёж и выдачу по плану приёмки, если инцидент затронул открытые заказы.

Версию опубликованного каталога сверяйте перед открытием приёма заказов отдельной командой с `--storefront`. [Проверка каталога](CATALOG.md#проверка-перед-приёмом-заказов)

## Рост ошибок API

Запустите наблюдатель на Linux-хосте развёртывания с Node.js 24. Укажите те же Compose-файлы, окружение и имя проекта, что при запуске стенда. Запрос выполняется внутри сети Compose. Публичный Caddy закрывает маршруты `/actuator`.

```sh
(
  while :; do
    if snapshot=$(timeout -k 3s 12s bash server/tooling/deployment-compose.sh --env-file /etc/crustcaper/stage/compose.env \
        --project-name crustcaper-stage \
        -f server/deploy/compose.yml -f server/deploy/compose.https.yml \
        exec -T edge wget -qO- -T 5 http://api:8080/actuator/commerceerrors 2>/dev/null); then
      printf '%s\n' "$snapshot"
    else
      printf '%s\n' '{}'
    fi
    sleep 60
  done
) | node server/tooling/api-error-watch.mjs
```

В знаменатель входят завершённые вызовы маршрутов API с ответом 2xx или 3xx и серверные ошибки 5xx. Ответы 4xx, preflight, статические файлы и опросы Actuator исключены. Снимок содержит идентификатор процесса и два накопительных счётчика. В журнал наблюдателя попадают события и обезличенные значения за интервал. Каждый наблюдатель читает один экземпляр API.

`ready` означает, что получен первый снимок. `incident` появляется после двух интервалов подряд с минимум тремя ошибками 5xx и долей ошибок от 5%. `recovered` появляется после двух интервалов с трафиком и долей строго ниже 5%. При отсутствии трафика инцидент остаётся открытым. Ошибка чтения, пауза без снимка дольше 90 секунд и перезапуск API отмечаются как `telemetry_unavailable`. `telemetry_restored` означает, что получен новый исходный снимок. После разрыва наблюдатель снова ждёт два подходящих интервала. Остановка потока завершает процесс с ошибкой, чтобы супервизор мог отдельно заметить пропажу наблюдения.

Направьте JSON в журнал дежурного и настройте оповещения по `incident`, `recovered` и `telemetry_unavailable`. При сигнале сопоставьте время с `api_request_failed` и проверьте затронутую операцию. Для исключений без записи `api_request_failed` проверьте журнал JVM и контейнера. Порог 5% и минимум три ошибки служат стартовой настройкой для одной точки. Перед открытием проверьте окно и пороги на типичном трафике. На стенде с синтетическими данными используйте `npm run test:storefront:api-errors`. [Процедура развёртывания](../README.md#single-host-https-staging)

## Фоновая сверка платежей

Для наблюдения за фоновой сверкой запустите второй поток с тем же Compose-проектом и периодом 60 секунд. В команде выше замените путь на `/actuator/paymentreconciliation` и передайте наблюдателю `--payment-reconciliation`. Снимок доступен внутри сети. Caddy возвращает 404 на публичном домене. Наблюдатель записывает результат только по счётчикам за интервал. В выводе отсутствуют идентификаторы процесса, заказов, клиентов и транзакций.

`incident` появляется после двух проблемных интервалов подряд. Проблемный интервал содержит ошибку проверки, отклонённый ответ, ошибку записи результата, ошибку прохода планировщика или ни одного завершённого прохода. При `recovered` два интервала подряд содержали завершённые проходы без ошибок. Если инцидент затронул проверку платежей, каждый из этих интервалов также содержит хотя бы один ответ провайдера с подтверждённым или ещё ожидающим платежом. Пустые проходы подтверждают работу планировщика. Они оставляют открытым инцидент проверки платежей.

`reconciliation_disabled` означает, что фоновая сверка выключена. Для выключенной сверки ожидаемые платежи проверяются в других каналах согласно регламенту. Разрыв потока, перезапуск API и сброс счётчиков требуют нового исходного снимка. Ранее открытый инцидент остаётся открытым до подтверждения восстановления. Подключите события к дежурному и при сбое сопоставьте их с **Payment review**, состоянием провайдера и журналом API. Меню и очередь кухни сохраняют доступность при ошибке проверки провайдера. [Фоновая сверка и повторные проверки](PAYMENTS.md)

## Сигналы менеджера

Раздел **Operations signals** показывает два счётчика для точки, к которой привязан менеджер. Проверьте время последнего обновления. При ошибке запроса значения помечаются как неизвестные. После восстановления связи панель получает их заново.

- **Payments without a kitchen order** показывает прямые заказы, у которых сервер подтвердил списание более минуты назад, а запись отсутствует в рабочей очереди. Откройте очередь и **Payment review**, затем сверяйте исходное списание с журналом провайдера и попросите дежурного проверить связку заказа и платежа в API. Используйте существующий заказ и прежний идентификатор операции. Этот сигнал измеряет состояние записи на сервере. Появление заказа на экране кухни проверяется отдельным сквозным сценарием.
- **Overdue fiscal receipts** показывает оплаченные заказы без прикреплённого чека через 30 минут после зафиксированной выдачи. Откройте **Fiscal receipts**. Панель начинает с выданных заказов без чека в порядке времени выдачи. Сверяйте сумму и номер заказа и прикрепите оригинал из EBM. Повторное обновление снимка покажет уменьшение счётчика после записи.

`GET /api/v1/operator/operations/signals` с сессией менеджера возвращает оба количества и время снимка без идентификаторов заказов и покупателя. Возраст платежа отсчитывается от первой подтверждённой записи, появившейся после миграции V21. Возраст чека рассчитывается по успешному переходу в `collected`. Для исторических записей без нужного времени используйте ежедневную сверку. Для оповещений при закрытой панели назначьте дежурного и настройте канал на инфраструктуре ресторана.

## Сигналы кухни

На открытой панели кухни и менеджера **New paid orders** показывает число оплаченных заказов, по которым ещё требуется нажать **Start preparing**. Надпись **Check this order** появляется после минуты ожидания. Для расчёта времени используются часы базы и `acceptedAt`, установленный в транзакции подтверждения оплаты. Заказ, созданный до этой миграции, остаётся в счётчике и очереди. Возраст для него не рассчитывается.

Чтобы получать звук, сотрудник включает **Enable order sound** после входа. Сигнал повторяется примерно раз в 20 секунд, пока в актуальной очереди есть заказы в ожидании приготовления. Кнопка **Mute order sound** оставляет визуальный сигнал. Звук работает в открытой вкладке при подтверждённой связи с сервером. [Правила Web Audio в Chrome](https://developer.chrome.com/blog/autoplay/#web-audio)

При сбое панель помечает последнюю очередь как устаревшую и приостанавливает переходы кухни до чтения актуального состояния. После восстановления соединения она запрашивает очередь заново. Для пилота измерьте время от подтверждения тестового платежа до появления заказа в панели на рабочем устройстве. Ориентир плана — до 10 секунд при рабочей сети. Затем проверьте повтор сигнала, отключение звука, потерю связи и начало приготовления на второй панели.

Сообщение **No paid orders are waiting** показывается после успешного чтения пустой очереди. При сбое уже загруженные карточки остаются видимыми с отметкой об устаревании. Если панель показывает **Support ID**, сотрудник передаёт этот идентификатор и время сбоя. Для обработанных серверных ошибок найдите `requestId` в событиях `api_request_failed`. Запись содержит шаблон маршрута, метод, статус, категорию и время обработки в миллисекундах. Если события нет, проверьте журнал API и контейнера за это время. При ошибке без идентификатора также проверьте журнал Caddy, доступность API и БД.

Если покупатель сообщает о сбое оформления или проверки оплаты, попросите **Support ID** и примерное время. Сверьте в журнале `api_request_failed` операцию и исход запроса. При сбое создания заказа или платежа сначала проверьте статус исходной операции, затем помогите покупателю продолжить оформление. Для поиска по номеру поддержки контактные данные, код выдачи и платёжные реквизиты не нужны.

В конфигурации из инструкции развёртывания выполните `stage_compose logs --tail 200 api`. Событие исключает URL запроса, его тело, данные авторизации и текст исключения. [Запуск HTTPS-стенда](../README.md#single-host-https-staging)

## Запросы по данным заказа

Покупатель открывает **Order privacy** из настроек приложения или со страницы меню. Для выбранного заказа он подтверждает телефон обычным SMS-кодом. Доступ действует десять минут в той же гостевой сессии. История заказов и восстановление оплаты используют свои правила доступа.

Веб-версия позволяет скачать JSON, а мобильная версия открывает системное меню, где покупатель может сохранить или передать JSON. Выгрузка содержит контактные данные и данные одного заказа. Фискальный PDF открывается отдельно на экране заказа.

Кнопка **Request deletion** отправляет запрос по одному заказу. Повтор возвращает тот же номер. **Pending review** означает, что запрос зарегистрирован. Менеджер своей точки открывает **Data requests**, сверяет номер заказа и нажимает **Start review**. Сервер записывает время и сотрудника. Менеджер передаёт номер запроса ответственному за обработку данных по закрытому каналу. Таблица менеджера содержит номера и время обработки.

Ответственный проверяет состав данных, необходимость хранения документов, запросы провайдерам и порядок ответа покупателю. Сам запрос и отметка о начале проверки сохраняют операционное состояние заказа, оплаты и чека. Для публичного пилота утвердите контакт, сроки, порядок исполнения и официальное уведомление об обработке данных. [Права субъекта данных в Руанде](https://dpo.gov.rw/dpp-law/rights-of-the-data-subject)

## Заказы площадок доставки

Администратор ресторана включает только площадки, с которыми у точки заключено соглашение. После применения Flyway администратор базы добавляет согласованные идентификатор канала и название в `operator_external_order_channels`. У одной точки может быть несколько площадок. ID состоит из строчных латинских букв, цифр, дефисов, точек или подчёркиваний. Отключённый канал скрывается из формы, а уже принятые заказы остаются в очереди до завершения.

```sql
INSERT INTO operator_external_order_channels (store_id, id, label, enabled)
VALUES (:'store_id', :'channel_id', :'channel_label', true)
ON CONFLICT (store_id, id) DO UPDATE
SET label = excluded.label, enabled = excluded.enabled;
```

Сотрудник выдачи или менеджер открывает **Add delivery order**, выбирает площадку, указывает внешний номер, время передачи по Кигали, позиции, количество и добавки. Номер переносится полностью, включая регистр и начальные нули. Вводите только состав для кухни и внешний номер. Контакт покупателя и адрес остаются в системе площадки.

Запись сразу появляется у кухни рядом с прямыми заказами. Кухня отмечает приготовление и готовность. При передаче курьеру сотрудник выдачи сверяет площадку и вводит внешний номер из подтверждения передачи. Менеджер может закрыть отменённый заказ до передачи. Дальнейшее оформление отмены, оплаты, чека и расчётов ведётся в согласованной системе площадки. Заказ площадки не занимает бронь прямого самовывоза.

Если ответ на регистрацию потерялся, повторите сохранение с теми же данными. Сервер возвращает прежний заказ даже после передачи или выключения площадки. Если по тому же сочетанию точки, площадки и номера уже есть заказ с другим составом или временем, сервер возвращает конфликт. Перед новым вводом найдите его в исходной системе и проверьте очередь, чтобы кухня не получила второй экземпляр.

При запоздавшем ответе на изменение панель сохраняет более новый статус, который уже получила из очереди. Если заказ успел уйти из рабочей очереди, панель сообщает об этом и запрашивает актуальные данные.

## Отмена до выдачи

Если ресторан не может выполнить заказ, менеджер выбирает **Cancel order** на его карточке, сверяет номер и подтверждает действие. Сервер убирает заказ из рабочей очереди, освобождает место в окне выдачи, удаляет код выдачи и останавливает ещё не отправленное уведомление о готовности. В журнале сохраняются предыдущий статус, время и учётная запись менеджера.

Покупатель видит `cancelled` и `refund_pending`. Исходная транзакция появляется в **Payment review** с причиной **Restaurant cancelled**. Менеджер оформляет полный возврат в Flutterwave и сверяет его по этой записи. При необходимости продавец оформляет корректировку в EBM по своему регламенту. [Возвраты Flutterwave](https://developer.flutterwave.com/docs/payment-operations/refunds)

## Проверка платежей

В разделе **Payment review** менеджер своей точки начинает с открытых исключений. Старые операции отображаются первыми. Проверенные возвраты доступны в истории. Панель загружает до 50 строк за запрос. Если записей больше, загрузите следующую страницу.

`GET /api/v1/operator/payment-exceptions?state=open` выдаёт открытые исключения, а `state=verified` — историю от новых записей к старым. Для продолжения передайте `nextCursor` из предыдущей страницы в параметре `after` с тем же состоянием. Сервер определяет сверку по записи о возврате конкретного списания. Поэтому сверка одного списания оставляет остальные исключения по заказу в очереди до их обработки. Старый запрос без параметров выдаёт 50 последних записей. Сервер проверяет роль `manager` и точку для просмотра и записи.

В панели Flutterwave найдите транзакцию по `providerTransactionId` и сверьте её с `merchantReference`. После завершения полного возврата в кабинете Flutterwave введите его идентификатор в **Payment review** и нажмите **Verify refund**. Spring запрашивает результат у провайдера, сверяет транзакцию, сумму, валюту и завершённое состояние, затем сохраняет проверку с именем менеджера. После подтверждения панель переносит операцию в историю. При потере ответа повторите проверку с тем же идентификатором возврата. После сверки возврата исходной оплаты по отменённому заказу покупатель увидит `refunded`. [Возвраты Flutterwave](https://developer.flutterwave.com/docs/payment-operations/refunds)

## Фискальные чеки

Фискальный оригинал оформляется в EBM фискального продавца. В разделе **Fiscal receipts** менеджер своей точки находит оплаченный заказ, сверяет оплаченную сумму, вводит номер с документа и прикрепляет исходный PDF размером до 1 МиБ. В очереди видны оплаченные заказы до и после выдачи, заявки без прикреплённого чека находятся в начале. [Системы EBM и подключение RRA](https://www.rra.gov.rw/en/ebm-electronic-billing-machine/request-and-install-ebm)

В очереди до 100 заказов. В неё также входят заказы с исходным чеком после подтверждённого возврата. Чтобы найти заказ за её пределами, введите его восьмизначный номер и нажмите **Find order**. Если короткий номер совпал у нескольких заказов, введите полный идентификатор заказа. Поиск ограничен точкой менеджера.

Сервер сверяет введённую сумму с оплаченным заказом в RWF и проверяет, что PDF открывается и содержит страницу. Повреждённый, зашифрованный или пустой документ отклоняется. Заказ продолжает ждать чек, чтобы менеджер мог приложить исходный PDF из EBM. При успешной выдаче сервер сохраняет байты файла, уникальный номер чека и запись менеджера. Покупатель получает файл через авторизованный экран заказа. Тот же доступ есть у гостя, который подтвердил телефон для этого заказа.

После подтверждения полного возврата в **Payment review** найдите заказ с исходным чеком в **Fiscal receipts**. Сформируйте корректировку в EBM, укажите её номер и положительную сумму возврата в целых RWF, затем прикрепите PDF размером до 1 МиБ. Сервер связывает документ с проверенным возвратом по тому же заказу и переводит чек в состояние **Corrected**. Повтор с тем же номером, суммой и файлом возвращает уже сохранённую запись. С экрана заказа доступны исходный чек и корректировка. Перед запуском проверьте выпуск обоих документов в EBM и согласуйте срок их хранения. [Инструкция подключённого выпуска](../../docs/runbooks/CONNECTED_RELEASE.md)

## Ежедневная сверка

Менеджер открывает **Daily reconciliation**, выбирает дату по Кигали и загружает CSV для сверки своей точки. Суммы в RWF берутся из записей CrustCaper. Сопоставьте строки с журналом кассы и EBM, транзакциями Flutterwave и выпиской по банку. Комиссии и фактические перечисления сверяйте по выпискам провайдера и банка.

| Строка отчёта | Дата и сумма |
| --- | --- |
| Принятый заказ | Сумма заказа и момент приёма после подтверждения оплаты. Последующая отмена или возврат отражается отдельной операцией. |
| Платёжное исключение | Сумма и дата записи конкретного позднего, повторного или заменённого списания. Сверка одного списания меняет состояние только его строки. |
| Отмена рестораном | Дата регистрации отмены. Сумма относится к исходному списанию и учитывается в его строке оплаты. |
| Проверенный возврат | Сумма и дата, когда менеджер подтвердил возврат в CrustCaper. |
| Прикреплённый чек | Сумма чека и дата его добавления в CrustCaper. Дату выдачи сверяйте с оригиналом из EBM. |

Неприкреплённые чеки в сводке относятся к принятым заказам выбранного дня, которые остаются оплаченными на момент просмотра. Открытые платёжные исключения этого дня считаются по состоянию на тот же момент. Если у старых принятых заказов отсутствует достоверная дата, их количество и сумма видны отдельно от разбивки по дням.

Используйте полный идентификатор заказа и идентификаторы платёжной попытки и транзакции при сопоставлении строк. Если платёжную попытку нельзя связать однозначно, её поля в строке остаются пустыми. При импорте CSV задайте текстовый тип для идентификаторов транзакций и возвратов, чтобы сохранить все цифры.

## Выдача доступа

На локальном сервере с `SPRING_PROFILES_ACTIVE=local` и провайдером `local` создаются синтетические сотрудники `demo-kitchen`, `demo-pickup` и `demo-manager` для тестовой точки. Пароль каждой локальной записи `local-demo-passphrase`. Префикс `demo-` зарезервирован для этих записей. Их пароли и сессии отвергаются вне локального режима даже при наличии строк в базе.

Для подключённой точки администратор БД создаёт отдельную учётную запись для каждого сотрудника. Сгенерируйте пароль и передайте его сотруднику по защищённому каналу. Генератор считывает пароль без отображения и выводит хеш. Из каталога `server/` после компиляции Java запустите его в интерактивном терминале.

```sh
java -cp build/classes/java/main com.crustcaper.api.operator.OperatorPasswordHash
```

Для собранного серверного JAR используйте тот же генератор через штатный загрузчик Spring Boot.

```sh
java -Dloader.main=com.crustcaper.api.operator.OperatorPasswordHash -cp crustcaper-api.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

Запустите [инструмент управления доступом](../tooling/operator-accounts.psql) через `psql` на выделенном подключении администратора. Для окружения настройте PostgreSQL service с проверкой имени сервера и утверждённым CA. Сверьте точку и точное имя базы. Введите хеш в приглашении PowerShell, чтобы сохранить его вне аргументов командной строки и истории оболочки. Пример выполняется из корня репозитория.

```powershell
$operatorDatabase = 'crustcaper_stage'
$operatorAccount = @{
    operation = 'create'
    storeId = 'kigali'
    accountId = [Guid]::NewGuid().ToString()
    username = 'staff-example'
    role = 'kitchen'
    passwordHash = Read-Host 'Paste the generated password hash' -MaskInput
}
try {
    $operatorAccount | ConvertTo-Json -Compress | ForEach-Object {
        [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes($_))
    } | psql -X --no-password --dbname='service=crustcaper-stage' -v "operator_database=$operatorDatabase" -f server/tooling/operator-accounts.psql
} finally {
    $operatorAccount.Remove('passwordHash')
}
```

Сохраните идентификатор сотрудника из результата в реестре доступа. Для смены пароля передайте `operation = 'rotate'`, тот же `storeId`, `accountId` и `username`, а также новый хеш без поля `role`. Смена пароля сбрасывает блокировку входа и отзывает все сессии в одной транзакции. Для прекращения доступа используйте `operation = 'disable'` и три поля идентификации. Отключённая учётная запись остаётся в истории действий. Повтор точной смены пароля и повтор отключения безопасны.

Используйте один и тот же UUID после неопределённого результата создания. Если инструмент сообщает о существующей записи, сверьте сотрудника и точку в реестре. Вывод инструмента содержит результат операции и число отозванных сессий. Хеш при передаче через stdin требует той же защиты, что и другие секреты.

### Первый менеджер из комплекта Linux

После запуска API и импорта реквизитов закрытой точки используйте интерактивный Bash на хосте. Выполняйте команды из корня распакованных исходников с той же функцией `portable_compose`, которая запускала стенд. Для административного подключения установите клиент PostgreSQL и настройте service `crustcaper-stage` с проверкой TLS-сертификата и имени сервера. [Переносимые образы](../README.md#transfer-verified-linux-images) · [Подготовка данных точки](CATALOG.md#подготовка-данных)

Сгенерируйте хеш пароля в контейнере API. Обычный `exec` в интерактивном терминале выделяет TTY, необходимый генератору. [Docker Compose exec](https://docs.docker.com/reference/cli/docker/compose/exec/) · [Spring Boot PropertiesLauncher](https://docs.spring.io/spring-boot/4.0/specification/executable-jar/property-launcher.html)

```bash
portable_compose exec api java \
  -Dloader.main=com.crustcaper.api.operator.OperatorPasswordHash \
  -cp /app/app.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

Укажите точное имя базы, точки и именную запись. Создайте UUID один раз и сохраните его в реестре доступа для привязки MFA и повторов.

```bash
operator_database='crustcaper_stage'
operator_store='kigali'
operator_username='manager-example'
operator_id=$(node -e 'process.stdout.write(require("node:crypto").randomUUID())')
printf '%s\n' "$operator_id"
```

Вставьте хеш в скрытое приглашение. Блок передаёт его через stdin в Node и `psql`.

```bash
(
  set +ax
  set -o pipefail
  unset operator_hash
  IFS= read -r -s -p 'Generated staff password hash: ' operator_hash < /dev/tty || exit 1
  printf '\n' >&2
  builtin printf '%s' "$operator_hash" | node -e '
    const [storeId, accountId, username] = process.argv.slice(1);
    const passwordHash = require("node:fs").readFileSync(0, "utf8");
    const request = { operation: "create", storeId, accountId, username, role: "manager", passwordHash };
    console.log(Buffer.from(JSON.stringify(request), "utf8").toString("base64"));
  ' "$operator_store" "$operator_id" "$operator_username" |
    psql -X --no-password --dbname='service=crustcaper-stage' \
      -v "operator_database=$operator_database" -f server/tooling/operator-accounts.psql
)
```

С теми же реквизитами сотрудника выполните [настройку аутентификатора](#аутентификатор-сотрудника). На переносимом стенде генератор использует ключ MFA из конфигурации запущенного API.

```bash
portable_compose exec api java \
  -Dloader.main=com.crustcaper.api.operator.OperatorTotpEnrollment \
  -cp /app/app.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

После подтверждения кода аутентификатора вставьте выданную зашифрованную строку привязки в скрытое приглашение. Затем проверьте вход менеджера на стенде с паролем и новым кодом.

```bash
(
  set +ax
  set -o pipefail
  unset operator_enrollment
  IFS= read -r -s -p 'Encrypted staff enrollment: ' operator_enrollment < /dev/tty || exit 1
  printf '\n' >&2
  builtin printf '%s\n' "$operator_enrollment" |
    psql -X --no-password --dbname='service=crustcaper-stage' \
      -v "operator_database=$operator_database" -f server/tooling/operator-accounts.psql
)
```

### Аутентификатор сотрудника

На подключённом стенде и в production для каждой записи обязательны пароль и код аутентификатора. Установите `CRUSTCAPER_OPERATOR_MFA_KEY` из хранилища секретов целевого окружения. Это отдельный ключ из 32 случайных байтов в Base64. Для восстановления базы храните резервную копию ключа в хранилище секретов. Прежние сессии, выданные только по паролю, при обновлении требуют нового входа.

После создания записи запустите генератор в интерактивном терминале с ключом этого же окружения. Он запрашивает точку, UUID и имя сотрудника. Добавьте выданный Base32-ключ в приложение-аутентификатор сотрудника с шестью цифрами и интервалом 30 секунд. Подтвердите текущий код в генераторе. Передавайте ключ аутентификатора сотруднику лично или по защищённому каналу. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238)

```sh
java -cp build/classes/java/main com.crustcaper.api.operator.OperatorTotpEnrollment
```

Для готового JAR запустите тот же генератор через Spring Boot.

```sh
java -Dloader.main=com.crustcaper.api.operator.OperatorTotpEnrollment -cp crustcaper-api.jar org.springframework.boot.loader.launch.PropertiesLauncher
```

Передайте выданную генератором строку с зашифрованной записью через stdin в уже настроенное административное подключение. Ввод действителен для UUID, точки и имени, указанных при генерации.

```powershell
$operatorDatabase = 'crustcaper_stage'
$enrollment = Read-Host 'Paste the encrypted enrollment payload' -MaskInput
try {
    $enrollment | psql -X --no-password --dbname='service=crustcaper-stage' -v "operator_database=$operatorDatabase" -f server/tooling/operator-accounts.psql
} finally {
    Remove-Variable enrollment
}
```

При утрате устройства администратор подтверждает личность сотрудника, выпускает новую привязку и применяет её к тому же UUID. Замена отзывает текущие сессии. Повтор уже применённого запроса оставляет действующую привязку и сессии в прежнем состоянии. Проверьте новый вход сразу после применения. Если для генератора использовался ключ другого окружения, выпустите новую привязку с ключом целевого сервера. При прекращении доступа отключите запись. Синхронизируйте часы сервера и телефона. После успешной авторизации дождитесь следующего кода для повторного входа.

На подключённом стенде назначьте реальные роли сотрудникам двух тестовых точек. Проверьте изоляцию очередей, работу после выхода и просрочки сессии, получение кода только покупателем и единственную выдачу при одновременном запросе. Сверьте историю с участником и конкретным SHA сборки.
