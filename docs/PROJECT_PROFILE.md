# Профиль CrustCaper Mobile

## Продукт и границы

Первый сценарий — гостевой заказ с самовывозом в одной точке в Кигали. Клиент видит меню и доступность, собирает корзину, выбирает окно выдачи, проверяет итог и возвращается к статусу заказа. Для пилота предусмотрены EN и RW, целые суммы в RWF, время выдачи в `Africa/Kigali`. Черновой перевод RW проверит носитель перед пилотом.

Роли продукта — гость, покупатель с подтверждённым контактом и сотрудники точки с раздельными правами. Мобильный контур проектируется для покупателя. Смена статусов кухни, управление запасами, сверка и возвраты относятся к общему серверу и операторскому контуру.

Первая реализация работает с синтетическими данными и адаптером для демонстрации. Рабочий путь проверяется от меню до текущего заказа, включая восстановление при перезапуске. Живой контракт общего API, платёжный провайдер, аккаунт и подтверждение контакта входят в подключённый контур.

## Платформы и среды

- React Native 0.83, Expo SDK 55, Expo Router, TypeScript, Node.js 24, npm. Команды перечислены в [AGENTS.md](../AGENTS.md).
- Пилотные минимумы заданы в конфигурации — Android 9 (API 28) и iOS 16. Проверить запуск на целевых версиях перед пилотом. Браузерное превью используется для разработки и обсуждения интерфейса.
- Демонстрационная сборка использует идентификатор `com.crustcaper.mobile.demo` и отдельную схему `crustcaper-demo`. Конфигурацию stage и production добавляет владелец выпуска при подключении соответствующего контура.
- Локальная среда и CI работают с демо-данными. Для подключения stage владельцу API нужно передать адрес, версию контракта, синтетические учётные данные и правила тестовой точки. Production использует отдельные ключи, адреса и права.
- Целевой бэкенд из плана — общий API сайта и приложения на Spring Boot и PostgreSQL. Мобильный клиент опирается на версионируемый серверный контракт и публичную конфигурацию окружения.

## Данные

| Данные | Граница |
| --- | --- |
| Меню, язык, версия каталога, корзина | Разрешён локальный кэш. При оформлении сервер заново проверяет состав, цену, слот и наличие. |
| Контакт, сессия и доступ к заказу | Реальные телефон, чек и история обрабатываются в согласованных средах; токены нативного клиента хранятся в защищённом хранилище. Сервер проверяет доступ к каждому заказу. |
| Платёж | Клиент хранит идентификаторы для восстановления. Сумму и статус подтверждает сервер. Ввод карты и Mobile Money происходит на платёжной странице согласованного PSP. |
| Диагностика | В логи и отчёты попадают версия, сценарий, класс ошибки и безопасный идентификатор корреляции. Телефон, токены, платёжные реквизиты и код выдачи исключены. |

## Нагрузка и критерии пилота

Черновые цели мобильного плана — p75 открытия меню до 3 секунд на LTE на бюджетном Android, crash-free sessions от 99,5% при достаточной выборке, обновление готовности заказа до 10 секунд при открытом приложении. Подключённая проверка включает минимум 20 пилотных заказов в целевых сборках. Цели требуют измерений на заданных устройствах, сети и сборках.

| Параметр | Кто и когда подтверждает |
| --- | --- |
| Определение сессии, пиковый поток, смесь API, трафик push и фоновых задач | Владелец продукта и владелец API строят паспорт из спроса пилотной точки перед стендовой нагрузкой. |
| SLO сервера, RPO/RTO и бюджет инфраструктуры | Ответственные за API и эксплуатацию согласуют по измеренному профилю и отрабатывают восстановление перед выпуском. |
| Регион, сроки удержания, удаление, доступ и допустимые провайдеры | Владелец данных утверждает реестр при подключении реальных пользователей, PSP или внешних SDK. |
| Версия API, список разрешённых PSP-хостов, signed build и назначенные ответственные | Владелец API и владелец выпуска фиксируют в записи допуска к подключённому пилоту. |

Именные владельцы и календарь выпуска пока не заданы. [Порядок приёмки](runbooks/MOBILE_RELEASE.md) фиксирует необходимые доказательства по средам.
