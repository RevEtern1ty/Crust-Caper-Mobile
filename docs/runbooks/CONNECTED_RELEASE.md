# Выпуск подключённого CrustCaper

## Кандидат

Зафиксируйте общий SHA сервера, OpenAPI и мобильного клиента. Прогон `Connected commerce CI` проверяет реальную PostgreSQL, гостевые сессии и обновление токена, цены, идемпотентность, авторизацию, локальную сверку оплаты и выдачу. `Mobile CI` проверяет отдельный демонстрационный профиль, экспорт и штатные нативные сборки. Фиксируйте результаты по конкретному SHA.

Задача `Public catalog and HTTPS checkout` собирает оба образа и запускает PostgreSQL, Caddy, сервер каталога и Spring Boot в отдельном проекте Compose. Chrome проверяет меню EN/RW, открытие заказа, защиту гостевой cookie и прохождение через тестовую платёжную страницу. Проверка подтверждает, что заявленный успех в URL сам по себе оставляет платёж в ожидании. После проверки сервером в базе остаётся одна оплаченная попытка.

### Локальный прогон HTTPS

Понадобятся Node.js 24, Java 21, Google Chrome, локальный Docker и свободные loopback-порты 80 и 443. Запустите из корня того же кандидата.

```sh
npm ci
npm --prefix storefront ci
npm --prefix storefront test
npm run build:storefront-test
(cd server && ./gradlew --no-daemon testClasses)
docker build -t crustcaper-api:storefront-test ./server
docker build -f storefront/Dockerfile -t crustcaper-catalog:storefront-test .
CRUSTCAPER_FIXTURE_API_IMAGE=crustcaper-api:storefront-test \
CRUSTCAPER_FIXTURE_CATALOG_IMAGE=crustcaper-catalog:storefront-test \
npm run test:storefront
```

На Windows используйте `gradlew.bat testClasses` из `server` и задайте две переменные образов через `$env:` перед запуском npm. Прогон сам останавливает и удаляет свою базу и контейнеры. Имитаторы оплаты и SMS находятся в тестовых классах. На этом прогоне используются синтетический каталог и локальный сертификат. Для внешнего стенда дополнительно выполните проверки ниже с выделенными тестовыми аккаунтами.

Команда `npm run test:storefront:catalog-photos` использует те же образы и запускает HTTPS-сценарий с отдельным каталогом фотографий. Она проверяет, что фото из API открывается в меню EN/RW и в карточке товара, а отсутствующие файлы возвращают `404`. В том же сценарии проверяются гостевой заказ и подтверджённая оплата.

Команда `npm run test:storefront:payment-restart` проверяет неопределённое состояние оплаты при сбое API. После оплаты у локального имитатора тест дожидается фонового запроса сверки и подаёт `SIGKILL` только контейнеру API одноразового проекта. PostgreSQL и контейнер имитатора продолжают работать. После запуска API тест ждёт фоновое подтверждение оплаты, затем проверяет один оплаченный заказ в базе и очереди кухни. Сценарий проходит без возврата покупателя и вебхука. JSON-отчёт сохраняется в `CRUSTCAPER_HTTPS_TEST_EVIDENCE_DIR`.

Команда `npm run test:storefront:kitchen-restart` добавляет к этому сценарию Chrome с открытой панелью кухни. Тест ждёт, пока панель покажет сбой опроса, и затем проверяет, что карточка единственного оплаченного заказа появилась автоматически в той же вкладке. Проверяются пустая очередь перед сбоем, первое звуковое оповещение после восстановления и отсутствие повторного сигнала при ближайших обновлениях. Штатный цикл напоминаний примерно раз в 20 секунд сохраняется, пока заказ ожидает приготовления.

Команда `npm run test:storefront:availability` проверяет внешние сигналы доступности на том же HTTPS-стенде. В синтетической точке приём заказов приостановлен. Тест по отдельности останавливает каталог и API в одноразовом проекте Compose и проверяет события сбоя и восстановления. Отчёт доступен в `CRUSTCAPER_HTTPS_TEST_EVIDENCE_DIR`.

Команда `npm run test:storefront:api-errors` проверяет частичный сбой создания котировки при доступных меню и базе. Тест использует одноразовый проект Compose, закрытый опрос счётчиков, два окна ошибок и два окна восстановления. Отчёт доступен в `CRUSTCAPER_HTTPS_TEST_EVIDENCE_DIR`.

Команда `npm run test:storefront:database-recovery` создаёт логическую копию при работающем API, останавливает исходный API и запускает тот же кандидат с восстановленной БД. Синтетический провайдер остаётся доступным в отдельном контейнере. Отчёт с контрольными сценариями и временем этапов сохраняется в `CRUSTCAPER_HTTPS_TEST_EVIDENCE_DIR`. [Восстановление PostgreSQL](../../server/docs/DATABASE_RECOVERY.md#репетиция-с-заказами)

### Нагрузочная проверка пилота на одной точке

После подготовки тех же образов и фикстур выполните `npm run test:storefront:load-smoke`, затем `npm run test:storefront:load`. Полный прогон планирует одно оформление каждые три секунды в течение трёх минут. Пятьдесят параллельных пользовательских циклов запрашивают меню со сдвигом расписания, суммарно десять раз в секунду. Параллельные повторы создания заказа и запуска оплаты используют тот же ключ идемпотентности. Отдельная группа из двенадцати покупателей одновременно претендует на четыре места в окне самовывоза.

Критерии прогона включают p95 меню до 500 мс по всем запросам и отдельно по ответам HTTP 200 с данными меню, а также p95 создания заказа до 1 000 мс без ожидания платёжного провайдера. Для каждого заказа измеряется время от получения клиентом подтверждённой оплаты до первого ответа API кухни с этим заказом. Ориентир составляет десять секунд при опросе раз в секунду под ролью кухни. PostgreSQL подтверждает одну оплаченную попытку на успешный заказ и соблюдение вместимости отдельного окна. Для сохранения JSON с числом операций и задержками задайте `CRUSTCAPER_HTTPS_TEST_EVIDENCE_DIR`.

Результаты характеризуют короткий локальный прогон с имитатором оплаты. Длительную нагрузку, сетевые задержки реального стенда и показ заказа на устройстве кухни измеряйте отдельно.

### Загрузка меню на медленной мобильной сети

На том же HTTPS-стенде выполните `npm run test:storefront:web-perf`. Chrome открывает `/menu/en` и `/menu/rw` по пять раз в новых мобильных контекстах 390 × 844 с DPR 2, отключённым браузерным кэшем и задержкой 150 мс. Скорость ограничена до 1,6 Мбит/с на загрузку и 0,75 Мбит/с на отправку. Тест сверяет правило замедления с запросом HTML в Chrome. Отчёт `storefront-web-perf.json` в `CRUSTCAPER_HTTPS_TEST_EVIDENCE_DIR` содержит результат каждой загрузки и p75 по языкам. Ориентиры составляют 2,5 с для LCP и 0,1 для CLS. [Методика LCP](https://web.dev/articles/lcp) · [Методика CLS](https://web.dev/articles/cls)

Chrome использует процессор машины прогона и синтетический каталог. Утвердите p75 и INP по реальным сеансам после запуска пилота.

## Конфигурация стенда

- Разверните API с профилем Spring `stage` за HTTPS и отдельной PostgreSQL. После успешной проверки readiness импортируйте утверждённый каталог с `store.open: false`. Импорт создаёт запись точки, которая нужна для создания именных сотрудников и привязки их аутентификаторов. Перед тестовыми заказами откройте точку на стенде и выполните `check-live-catalog.mjs` с `--checkout` на публичном домене. Проверка сверяет точку и версию, HTML обеих локалей, фото и переход от карточки блюда к приложению оформления. [Запуск сервера](../../server/README.md) · [Проверка каталога](../../server/docs/CATALOG.md#проверка-перед-приёмом-заказов)
- Запустите внешнее наблюдение за тем же HTTPS-доменом и настройте доставку сигнала дежурному. Проверьте получение событий сбоя и восстановления на пилотном стенде. [Проверка доступности](../../server/docs/OPERATIONS.md#проверка-доступности-снаружи)
- Запустите чтение счётчиков запросов и фоновой сверки внутри сети Compose. Проверьте публичный ответ 404 на `/actuator/commerceerrors` и `/actuator/paymentreconciliation`. Настройте получение сигналов об ошибках, восстановлении и потере телеметрии. Уточните пороги на трафике пилота. [Рост ошибок API](../../server/docs/OPERATIONS.md#рост-ошибок-api) · [Фоновая сверка платежей](../../server/docs/OPERATIONS.md#фоновая-сверка-платежей)
- Задайте отдельный ключ шифрования аутентификаторов и привяжите аутентификатор к каждой именной записи кухни, выдачи и менеджера. Проверьте вход, отказ при пропущенном коде и при повторе принятого кода, отзыв прежней сессии после замены аутентификатора и отзыв доступа при отключении записи. [Выдача доступа](../../server/docs/OPERATIONS.md#выдача-доступа)
- Разверните API с ротацией гостевых сессий перед распространением новой мобильной сборки. При откате сохраняйте API, поддерживающий ротацию, пока на устройствах могут оставаться незавершённые обновления токена. Проверьте повтор после потери ответа на обновление и выход из уже выданного заказа. [Контракт гостевой сессии](../../contracts/README.md)
- Снимите резервную копию стенда и восстановите в новую базу на отдельном экземпляре PostgreSQL. Проверьте Flyway, оплату, статусы и чеки через API. Зафиксируйте время восстановления и согласуйте периодичность копирования с владельцем эксплуатации. [Восстановление базы](../../server/docs/DATABASE_RECOVERY.md)
- Сверьте в разделе **Daily reconciliation** день по Кигали, первоначальную оплату, возврат в другой день и прикреплённый чек. Сопоставьте CSV с тестовыми выписками провайдера и кассы. Проверьте, что отмена и неверифицированный возврат не увеличивают оборот. [Ежедневная сверка](../../server/docs/OPERATIONS.md#ежедневная-сверка)
- На изолированных данных проверьте в **Operations signals**, что обычный принятый кухней платёж и платёж в очереди исключений не повышают счётчик пропавших заказов. Воспроизведите пропавшую запись, просроченный чек и прикрепление документа. Проверьте, что при сбое чтения панель отмечает значения как неизвестные, а учётным записям кухни и выдачи данные недоступны. [Сигналы менеджера](../../server/docs/OPERATIONS.md#сигналы-менеджера)
- Настройте Flutterwave Test, webhook `/api/v1/webhooks/flutterwave` и HTTPS-возврат на `/payment-return`. Сначала проверьте на тестовых контактах успешный платёж, отказ, потерю возврата, дубль webhook и изменение цены или времени выдачи. Сверьте заказ, транзакцию и очередь ресторана. [Платёжный контур](../../server/docs/PAYMENTS.md)
- Проверьте фоновую сверку, закрыв приложение после оплаты и изолировав тестовый webhook. Для проверки восстановления включите отдельный Twilio Verify Service в среде `stage`, откройте приложение с новой гостевой сессией и подтвердите номер по SMS. Сверьте доступ к одному заказу, отказ для неверного кода, отсутствие права на чужую оплату и ограничения повторов. [Контур восстановления](../../server/docs/ORDER_RECOVERY.md)
- Для двух сохранённых заказов проверьте восстановление после смены гостевой сессии. Подтвердите доступ к первому, затем откройте второй из истории. Действие подтверждения телефона должно открыть форму с номером выбранного заказа. После SMS проверьте исходный заказ, сумму и количество платёжных попыток.
- Оставьте заказ с неопределённой оплатой открытым. После 18 секунд ожидания приложение должно показывать сообщение о задержке и проверять статус через 15 секунд, а после двух минут через 60 секунд. Проверьте немедленное ручное обновление, свежий запрос при возвращении в приложение и переход на обычный интервал статуса кухни после подтверждения оплаты.
- На изолированном стенде проверьте просроченную бронь с неопределённой оплатой в Payment review. Менеджер точки видит `tx_ref`, может запросить результат и после подтверждённого позднего списания получает исключение для возврата. Проверьте отказ для менеджера другой точки и отсутствие заказа в очереди кухни. [Сверка менеджером](../../server/docs/PAYMENTS.md#сверка-менеджером)
- Оформите фискальный оригинал в EBM выбранного продавца. Проверьте прикрепление его PDF менеджером и получение покупателем на Android/iOS. На Flutterwave Test завершите возврат через кабинет мерчанта, подтвердите его в панели менеджера и сверьте клиентский статус. Проверьте повтор операции и запрет для сотрудника другой роли или точки. [Фискальные чеки и возвраты](../../server/docs/OPERATIONS.md)
- Отмените оплаченный и ещё не выданный заказ от имени менеджера. Проверьте исчезновение из кухни, освобождение места в ещё открытом окне и клиентский статус отмены с ожидаемым возвратом. Сверьте возврат именно исходной оплаты в Flutterwave Test и подтвердите новый статус на клиенте. [Отмена до выдачи](../../server/docs/OPERATIONS.md#отмена-до-выдачи)
- Оставьте готовый заказ открытым у покупателя и завершите выдачу на панели. Клиент должен обновить статус и скрыть код выдачи даже после временного сбоя запроса статуса. Повторите с отменой готового заказа. Проверьте возобновление после возврата в приложение и остановку фонового опроса после закрытия экрана.
- После получения котировки добавьте выбранное блюдо в стоп-лист из панели менеджера. Проверьте, что прежняя котировка отклоняется, покупатель видит изменение и может отредактировать корзину. При паузе новых заказов сверьте действующие брони и работу очереди кухни. Возобновите приём и подтвердите новую покупку. [Каталог и доступность](../../server/docs/CATALOG.md)
- Выберите будущее окно и попробуйте снизить лимит после того, как покупатель занял место. Проверьте отказ для значения ниже числа броней, а затем снизьте лимит до числа занятых мест. По прежней котировке дополнительный заказ должен получить отказ. Проверьте оплату по действующей брони и появление свободного места после увеличения лимита. [Лимиты самовывоза](../../server/docs/CATALOG.md#лимиты-самовывоза)
- Опубликуйте из панели менеджера будущий диапазон окон по времени Кигали. Сверьте опубликованные окна с меню покупателя и оформите заказ на одно из них. Проверьте отказ при пересечении с существующим окном и обновление панели после повтора запроса, ответ на который потерян. [Публикация окон](../../server/docs/CATALOG.md#публикация-окон-самовывоза)
- В открытой панели кухни сравните момент подтверждения тестовой оплаты с появлением оплаченного заказа. Ориентир пилота — до 10 секунд при работающей сети. Убедитесь, что сигнал сохраняется до начала приготовления, а потеря связи помечает очередь и останавливает звуковое оповещение. Проверьте звук на устройстве кухни. [Сигналы кухни](../../server/docs/OPERATIONS.md#сигналы-кухни)
- При выдаче оборвите ответ после успешной записи. Панель должна проверить этот заказ на сервере и подтвердить выдачу под текущей учётной записью. Если проверка тоже недоступна, используйте Refresh после восстановления связи. Повторите с параллельной отменой и сверьте единственную запись о выдаче в журнале.
- Добавьте тестовый заказ включённой площадки и проверьте, что он появился в общей очереди рядом с прямым заказом. Повторите регистрацию с теми же данными, проверьте отказ при изменённом составе, приготовьте заказ и подтвердите передачу по внешнему номеру. Сверьте роли, точки и журнал переходов. [Заказы площадок доставки](../../server/docs/OPERATIONS.md#заказы-площадок-доставки)
- Для уведомления о готовности настройте отдельный проект Expo, учётные данные FCM и APNs и задайте серверные параметры доставки. На подписанных сборках проверьте согласие, отказ и отзыв для отдельного заказа, получение при закрытом приложении и переход к авторизованному заказу по нажатию. [Уведомления о готовности](../../server/docs/PICKUP_ALERTS.md)
- Задайте публичные переменные `CRUSTCAPER_API_BASE_URL` (HTTPS до `/api/v1`), `CRUSTCAPER_STORE_ID`, `CRUSTCAPER_PSP_HOSTS` (список точных хостов) и `CRUSTCAPER_APP_LINK_ORIGIN`. Для production также требуются закреплённые `CRUSTCAPER_ANDROID_PACKAGE` и `CRUSTCAPER_IOS_BUNDLE_ID`. Клиент не получает серверных секретов.
- Направьте домен `CRUSTCAPER_APP_LINK_ORIGIN` на Spring Boot для `/.well-known/apple-app-site-association`, `/.well-known/assetlinks.json` и `/payment-return`. Можно использовать один HTTPS-домен для API и возврата. Путь в `CRUST_PAYMENT_RETURN_URL` должен быть `/payment-return`. Публикуйте JSON по HTTPS с `200` без перенаправлений и проверяйте снаружи сети стенда. [Apple Associated Domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains) · [Android App Links](https://developer.android.com/training/app-links/configure-assetlinks)
- На сервере задайте `CRUSTCAPER_APP_LINK_IOS_APP_ID` с полным Apple Application Identifier, включая App ID Prefix и bundle ID. Для Android задайте `CRUSTCAPER_APP_LINK_ANDROID_PACKAGE` и `CRUSTCAPER_APP_LINK_ANDROID_FINGERPRINTS` с SHA-256 сертификатов подписи используемых сборок через запятую. При Play App Signing нужен сертификат приложения из Play Console. При отсутствии данных платформа получает `404` для своего association-файла. Проверьте совпадение идентификаторов с Expo и подписанными артефактами.
- С машины вне сети стенда запустите `node server/tooling/check-app-links.mjs` с аргументами `HTTPS_ORIGIN PAYMENT_RETURN_URL ANDROID_PACKAGE CERT_SHA256 IOS_APP_ID`. Возьмите origin из подписанной сборки, а URL возврата из фактически развёрнутого `CRUST_PAYMENT_RETURN_URL`. Используйте SHA-256 сертификата подписанного приложения в формате из пар шестнадцатеричных цифр через двоеточие. Команда проверяет совпадение origin, HTTPS, опубликованные ассоциации и страницу возврата. Затем откройте ссылку на телефонах с подписанными сборками.
- В браузере `/payment-return` показывает инструкцию открыть Orders. Мобильный экран дожидается восстановления журнала, открывает известный устройству заказ из ссылки и запрашивает актуальный статус через API. При пропущенном или неизвестном номере открывается активный заказ. Параметры результата провайдера не отражаются в HTML и не управляют статусом. В прокси исключите параметры URL возврата из журналов.

## Подпись и приёмка

Профили `stage` и `production` в `eas.json` предполагают проект Expo и аккаунты магазинов владельца. Стенд выпускается для внутренней раздачи, production — как подписанные AAB и IPA. Перед выпуском проверьте App Links на этих же подписанных артефактах, лимиты сетевых запросов, восстановление после перезапуска, точные версии ОС и поведение экранного диктора. [Подпись EAS](https://docs.expo.dev/app-signing/app-credentials/)

На пилоте подтвердите тестовый заказ и возврат платежа в каждой нативной сборке. Оператор сверяет кухню, выдачу, учёт возвратов и фискальный документ. Утвердите реальные фотографии, состав и аллергены, перевод, хранение и удаление контактных данных, поддержку, план инцидентов и остановки раскатки. Затем владелец принимает решение о допуске подписанного кандидата. [Матрица приёмки](MOBILE_RELEASE.md)

Проверьте `/privacy` с обоих меню. Гость подтверждает телефон, скачивает JSON одного заказа и дважды отправляет запрос на удаление. Сверьте номер и состояние запроса. Отдельно проверьте запрет экспорта без свежего OTP, запрет записи с чужого веб-источника и изоляцию по учётным записям сотрудников. Менеджер берёт запрос в работу, покупатель видит обновлённый статус, оплаченный заказ по-прежнему доступен. До пилота согласуйте порядок исполнения запросов и опубликуйте утверждённые документы. [Запросы по данным заказа](../../server/docs/OPERATIONS.md#запросы-по-данным-заказа)
