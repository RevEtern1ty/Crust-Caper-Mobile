# Приёмка и выпуск CrustCaper Mobile

## Матрица приёмки демонстрации

Установите зависимости через `npm ci`, затем запустите `npm run check`, `npm run build:web` и `npm run test:web`. Используйте синтетические данные. Сборку, тесты и просмотр привязывайте к одному кандидату.

| Контур | Что проверить | Доказательство |
| --- | --- | --- |
| Маршруты и экран | Меню, блюдо и добавки, корзина, оформление, оплата, заказ, самовывоз и настройки. Открытие напрямую, путь назад, пустые и ошибочные состояния. | Матрица Web на 320, 390 и 430 px. Для EN/RW, длинного текста и крупного шрифта проверены отсутствие переполнения, видимость действий, прокрутка и фокус. Сохранены снимки затронутых состояний. |
| Цена, время и платёж | Блюдо и модификаторы, изменение корзины, окно выдачи, истечение предложения, повтор подтверждения, отказ/ожидание/успех. | Итог совпадает в обзоре, платеже и заказе. На одно подтверждение создаётся один заказ. Зафиксированы ожидаемый и фактический статус. |
| Восстановление | Перезагрузка на промежуточном статусе, повтор после задержки, конкурентные вкладки и навигация назад. Для проблем хранения проверить повреждённый или устаревший снимок. | Сценарий регрессии фиксирует сохранённые данные и итог после повторного входа. Незавершённый заказ можно восстановить, устаревший не блокирует новый. |
| Доступность | Клавиатура и последовательность фокуса на Web. На устройствах проверить крупный системный шрифт, safe area, системную клавиатуру, жест назад, TalkBack и VoiceOver. | Автотест проверяет доступные роли и действия. Ручной проход фиксирует устройство, ОС и наблюдённое поведение. |

## Подтверждение нативных сборок

- `build:android` и `build:ios` проверяют экспорт JS. В Android CI для `demo` и `stage` сборка с отладочной подписью проходит проверку пакета, минимума Android, разрешений, параметров резервного копирования, ABI и встроенного JS. Затем этот же APK устанавливается в эмулятор Android 35 x86_64. Проверка сверяет хеш установленного файла и выполняет два холодных запуска без сети и Metro. Оба раза приложение должно оставаться активным минимум десять секунд. Сверьте SHA запуска и контрольную сумму APK.
- В Android `demo` видны демонстрационный каталог и нижние вкладки. В `stage` без сети видны вкладки и предложение повторить загрузку меню. Артефакт `mobile-android-*-emulator-smoke-*` сохраняет дерево интерфейса, снимки и сведения об APK и Android. При сбое он содержит доступную диагностику. Обычный артефакт APK сохраняется после успешной проверки. [ADB и запуск приложения](https://developer.android.com/tools/adb) · [Эмулятор Android](https://developer.android.com/studio/run/emulator-commandline)
- `Build and launch iOS demo on simulator` собирает Release без подписи разработчика, проверяет идентификатор, минимальную версию iOS, режим транспортной безопасности и встроенный JS. Задание устанавливает приложение на симулятор iPhone, запускает его без Metro и прикладывает снимок. Полный заказ и TestFlight проверяются отдельно.
- Перед нативной сборкой установите зависимости через `npm ci`. Установка переносит в закреплённый Expo Sharing исправление завершения системной отправки на iOS. Для проверки изменения нужен новый iOS-бинарник. [Исправление Expo](https://github.com/expo/expo/blob/40f0a6f6711d93762e0506b37e6e077e4bd9a541/packages/expo-sharing/ios/SharingModule.swift#L19-L29)
- На физическом Android установите APK нужного профиля и пройдите меню до текущего заказа. Закройте приложение, запустите его и проверьте восстановление. На iOS повторите сценарий в установленной нативной сборке. Проверки на эмуляторе и физическом устройстве фиксируйте отдельно.
- Для PR укажите SHA, фактически проверенный Actions. Если прогон выполнен для результата предварительного слияния, укажите также SHA ветки. Статусы прогонов и снимки относятся только к соответствующему кандидату.

Для отдельного прогона Android используйте корень проекта и один уже загруженный изолированный эмулятор. Передайте путь к собранному APK, его профиль и каталог результатов.

```sh
evidence_dir=$(mktemp -d)
bash tooling/android-emulator-smoke.sh android/app/build/outputs/apk/release/app-release.apk demo "$evidence_dir"
```

### Заказ в локальном Android APK

Соберите APK профиля `local` из чистой копии проверяемого SHA. Вариант для Linux использует образ `reactnativecommunity/react-native-android@sha256:71884cd2953769cdaedced1922970d3168d9028f74f78246c5f0cbc6d60598df`. В нём установлены JDK 17, Android API 36, Build Tools 36.0.0, CMake 3.30.5 и NDK 27.1.12297006. Подключите Node.js 24.22.0 согласно `.nvmrc` для установки зависимостей и сборки JS. [Dockerfile v20.1](https://github.com/react-native-community/docker-android/blob/v20.1/Dockerfile) · [Node.js 24.22.0](https://nodejs.org/dist/v24.22.0/)

Адрес `10.0.2.2` доступен из Android Emulator и ведёт на loopback хоста. В примере API слушает `127.0.0.1:18080` на хосте эмулятора. [Адреса эмулятора](https://developer.android.com/studio/run/emulator-networking-address)

При сборке модуль `react-native-safe-area-context` запрашивает Build Tools 35.0.0, а приложение и `expo-modules-core` используют CMake 3.22.1. Команда ниже добавляет недостающие версии через `sdkmanager` с уже принятыми в образе лицензиями.

```sh
set -eu
node_dir=$(mktemp -d)
curl -fsSL https://nodejs.org/dist/v24.22.0/node-v24.22.0-linux-x64.tar.gz -o "$node_dir/node.tar.gz"
printf '28ea0a438de9a13bd7891fd758eee6c7819ee8af5442dfd8d45bd65e56d4228c  %s\n' "$node_dir/node.tar.gz" | sha256sum -c -
tar --no-same-owner -xzf "$node_dir/node.tar.gz" -C "$node_dir"
export PATH="$node_dir/node-v24.22.0-linux-x64/bin:$PATH"

export CI=1 NODE_ENV=production EXPO_NO_TELEMETRY=1 CRUSTCAPER_BUILD_PROFILE=local CRUSTCAPER_STORE_ID=kigali
export CRUSTCAPER_API_BASE_URL=http://10.0.2.2:18080/api/v1
export CMAKE_BUILD_PARALLEL_LEVEL=1
for package in 'build-tools;35.0.0' 'cmake;3.22.1'; do
  if [ ! -f "$ANDROID_HOME/${package%;*}/${package#*;}/source.properties" ]; then
    "$ANDROID_HOME/cmdline-tools/latest/bin/sdkmanager" --sdk_root="$ANDROID_HOME" \
      --install "$package" </dev/null
  fi
done
npm ci
npx --no-install expo prebuild --platform android --no-install
(
  cd android
  bash ./gradlew --no-daemon --max-workers=1 :app:assembleRelease \
    '-Dorg.gradle.jvmargs=-Xmx1400m -XX:MaxMetaspaceSize=512m -XX:ActiveProcessorCount=2 -Dfile.encoding=UTF-8' \
    -Pkotlin.compiler.execution.strategy=in-process \
    -PreactNativeArchitectures=x86_64 -Pandroid.builder.sdkDownload=false
)
apk=android/app/build/outputs/apk/release/app-release.apk
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --print-certs "$apk"
sha256sum "$apk"
```

Запустите JAR этого же кандидата с Java 21, профилем Spring `local` и `CRUSTCAPER_PORT=18080`. Используйте отдельную PostgreSQL со свежими синтетическими данными и пустой очередью кухни. Проверьте готовность API на `http://127.0.0.1:18080/actuator/health/readiness`. Перенесите APK из среды сборки на хост эмулятора и запустите тест из корня репозитория с Python 3.11 или новее. Нужен один загруженный изолированный x86_64-эмулятор с английским интерфейсом, включённой сетью и без перенаправлений ADB. Сценарий запускается без Metro. [Запуск API и PostgreSQL](../../server/README.md#local-integration)

```sh
evidence_dir=$(mktemp -d)
python3 tooling/android-connected-checkout.py /path/to/app-release.apk "$evidence_dir"
```

Сценарий проверяет установку того же APK, заказ через мобильные экраны, восстановление текущего заказа после холодного запуска, тестовую оплату, приготовление и выдачу. После выдачи код исчезает, статус сохраняется при повторном запуске. Сохраните SHA исходников и APK, версию эмулятора и результаты `evidence.json`, `menu.png` и `collected.png`. Эта сборка имеет отладочную подпись и ABI x86_64. Подписанные сборки, реальные платежи и приёмка на физических устройствах проходят по следующей матрице.

Для кандидата с выходом из гостевой сессии добавьте `--check-session-end`. Сценарий завершит сессию через настройки после выдачи, перезапустит приложение и подтвердит пустую историю. Снимок `session-ended.png` фиксирует ответ настроек.

Для проверки позднего чека передайте `--late-receipt-pdf /path/to/TEST_RECEIPT.pdf` с синтетическим PDF из локального комплекта. Менеджер прикрепит его после выдачи, пока экран покупателя открыт. Сценарий дожидается кнопки **Share receipt** без ручного обновления и сохраняет снимок `receipt-after-pickup.png`.

Для проверки обновления передайте `--upgrade-from /path/to/previous.apk`. Обе сборки должны иметь один ID приложения, адрес API и сертификат подписи. Сценарий начнёт заказ в предыдущей сборке, установит кандидат поверх неё с сохранением данных и продолжит тот же заказ до выдачи. Сохраните хеши обеих сборок и снимки до и после обновления.

Для прогона по USB соберите профиль `local` с `CRUSTCAPER_API_BASE_URL=http://127.0.0.1:18080/api/v1` и ABI устройства. Запустите локальный стенд на компьютере, подключите Android с включённой USB-отладкой и найдите серийный номер через `adb devices`. Подставьте его вместо `SERIAL`.

```sh
adb -s SERIAL reverse --no-rebind tcp:18080 tcp:18080
adb -s SERIAL install -r /path/to/app-release.apk
```

Откройте CrustCaper и пройдите тестовый заказ. После прогона уберите созданное перенаправление командой `adb -s SERIAL reverse --remove tcp:18080`. Для автоматического прогона такой сборки в изолированном эмуляторе передайте `--adb-reverse` и оставьте управление перенаправлением сценарию. [Подключение Android по USB](https://reactnative.dev/docs/running-on-device)

### Данные заказа в Android

Запустите тот же профиль Spring `local` на одноразовой базе с пустой очередью кухни и включите `CRUSTCAPER_ORDER_ACCESS_PROVIDER=local`. Используйте отдельный ADB-сервер на loopback и один загруженный эмулятор. Для APK с адресом `127.0.0.1` запустите проверку с фактическими именем AVD, серийным номером и SHA-256 APK.

```sh
evidence_dir=$(mktemp -d)
ADB_SERVER_SOCKET=tcp:127.0.0.1:15042 python3 tooling/android-order-privacy.py "$apk" "$evidence_dir" \
  --serial "$serial" --avd-name "$avd_name" --apk-sha256 "$apk_sha256" --adb-reverse --check-share
```

Сценарий создаёт синтетический оплаченный заказ через локальный API. В приложении он проверяет сохранение SMS-запроса и очистку поля кода после возврата из фона, отправку запроса на удаление и отображение статуса после проверки менеджером. При `--check-share` сценарий открывает и закрывает системный экран отправки без выбора получателя. На подписанных Android и iOS сохраните `crustcaper-order-data.json` и проверьте, что он открывается и содержит данные только подтверждённого заказа. Сохраните `evidence.json` с хешем установленного APK и `privacy-in-review.png` со статусом запроса. Для публичного пилота повторите проверку с SMS-провайдером на подписанных сборках.

На iOS откройте чек синтетического заказа, выберите **Print** и отмените печать. Действия экрана должны снова стать доступны. Откройте тот же чек ещё раз, сохраните PDF в Files и сверьте его с исходным файлом. Для экспорта данных заказа отмените выбранное действие при доступности такого сценария и снова откройте JSON. Зафиксируйте версию iOS, SHA сборки и исход обоих повторов. Используйте синтетические документы для снимков и журналов.

Для этой проверки на Mac с Apple Silicon запустите локальный API с синтетическим каталогом и предварительно загрузите выделенный симулятор iPhone. В корне чистой копии кандидата укажите UUID этого симулятора. Скрипт оставит предварительно загруженный симулятор открытым для проверки чека.

```sh
npm ci
evidence_dir=$(mktemp -d)
CRUSTCAPER_IOS_SIMULATOR_UDID='<iPhone-simulator-UUID>' \
CRUSTCAPER_API_BASE_URL=http://127.0.0.1:18080/api/v1 \
  bash tooling/ios-simulator-smoke.sh "$evidence_dir" local
```

## Закрытые сборки для Play Internal и TestFlight

Профиль `stage` предназначен для прямой установки APK и iOS-сборки с внутренним профилем подписи. `stage-store` наследует окружение EAS `preview` и настройки приложения `stage`, выпускает AAB для Play Internal и IPA для TestFlight. У обеих stage-сборок идентификатор `com.crustcaper.mobile.stage`. Для публичной раскатки используйте профиль `production` с его окружением и идентификаторами. Все профили EAS используют версию Node.js из `.nvmrc`. [Профили Expo Build](https://docs.expo.dev/build/eas-json/) · [Внутренняя раздача](https://docs.expo.dev/build/internal-distribution/)

1. Владелец связывает исходники с проектом Expo, задаёт публичные параметры API, точки, PSP и App Links в окружении EAS `preview`, регистрирует приложение stage в Play Console и App Store Connect, настраивает подпись. Перед раздачей сверьте ассоциации stage-домена с сертификатом, которым Play подписывает приложение, и идентификатором Apple App ID. [Настройка подключённой среды](CONNECTED_RELEASE.md#подпись-и-приёмка)
2. Номера сборок `versionCode` и `buildNumber` для `stage-store` увеличивает EAS. Если сборки с идентификатором stage уже загружались, задайте в EAS последние номера для каждого магазина через `eas build:version:set --profile stage-store` до создания следующей сборки. [Управление версиями](https://docs.expo.dev/build-reference/app-versions/)
3. После настройки учётных записей соберите артефакты. Загрузку выполните отдельно после сверки SHA, идентификатора и номера сборки.

   ```bash
   eas build --profile stage-store --platform android
   eas build --profile stage-store --platform ios
   ```

4. Загрузите AAB в раздел Internal testing приложения stage в Play Console, а IPA в запись stage в App Store Connect. Добавьте тестеров в соответствующие группы и выполните подключённую приёмку на установленных из магазинов сборках. [Google Play](https://docs.expo.dev/submit/android/) · [TestFlight](https://docs.expo.dev/submit/testflight/)

## Подключённая приёмка

1. Зафиксировать SHA, изолированную среду, OpenAPI, данные тестовой точки, устройства, ОС и сеть. В Android-пилоте взять бюджетный и современный телефоны, в iOS — iPhone 11 и доступную актуальную модель.
2. Пройти гостевой заказ, конфликт цены, конкуренцию за слот, стоп-лист, отсутствие сети и повтор старого заказа. Проверить доступ из чужой и отозванной сессий.
3. Пройти успешную, отклонённую и задержанную оплату с провайдером, возврат, повторный tap, потерю redirect, рестарт и смену Wi‑Fi на LTE. Для каждой платформы сверить заказ и возврат с PSP, кухней и EBM. После отключения push подтвердить доступность готовности в приложении.
4. Зафиксировать доказательства Android AAB и iOS TestFlight, инвентаризацию SDK и данных, правила магазинов на дату подачи, результаты подключённого пилота и решение ответственного владельца.

## Реакция на сбой

| Наблюдение | Действие и контроль |
| --- | --- |
| Оформление или статус массово недоступны | Определить затронутый релиз и окно, приостановить раскатку. Сверить состояние общей системы; повторить контрольный заказ перед возобновлением. |
| Исход оплаты неизвестен | Найти исходный заказ и попытку. Сверить с доверенным статусом PSP. Повтор допустим после окончательного результата или через согласованный повтор с тем же ключом. |
| Дефект клиента затрагивает деньги, права или данные | Приостановить затронутый путь и привлечь владельца API и выпуска. Проверить поддержку предыдущего клиента и восстановление до расширения раскатки. |

## Запись доказательств

Для каждого дефекта укажите симптом, среду и исходный SHA. Зафиксируйте воспроизведение, исправление, команду регрессии, SHA кандидата и наблюдаемый исход. В отчёте по кандидату доступны статусы «пройдено», «не пройдено» и «не проверялось» с указанием причины. Для визуальной проверки приложите ссылку на снимок, экран, локаль, размер и итог просмотра. Действия с недостоверной ценой, двойным заказом и потерей сохранённых данных блокируют допуск затронутого сценария.

Для выпуска нужны артефакт с подписью, пробная раскатка, окно наблюдения, способ остановки и решение ответственного за выпуск. Приложите отдельные строки доказательств для браузера, экспорта JS, APK или AAB, iOS, реального устройства и подключённой оплаты.
