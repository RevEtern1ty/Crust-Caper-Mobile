# Контракт общего API CrustCaper

[OpenAPI 0.8](openapi.draft.yaml) описывает реализованные в Spring Boot маршруты меню, гостевой сессии, котировки, заказа, восстановления и оплаты. Мобильный клиент обращается к ним через [HTTP-адаптер](../src/live/http-api.ts). Для сессии используются непрозрачные access и refresh токены. Сервер хранит хеши и сроки действия. Access действует 20 минут, refresh по умолчанию действует 90 дней. При потере ответа клиент может повторить обновление с тем же refresh токеном и сохранить доступ к заказам исходного гостя. Время жизни старого access сохраняется до его истечения. Исходная сессия управляет оплатой, повтором запроса создания по ключу и доступом к заказу. Подтверждение телефона выдаёт дополнительный доступ на просмотр и повтор покупки.

Котировка привязана к границам окна самовывоза. Создание заказа сверяет время, позиции, цены, налоги и свободную квоту под блокировкой слота. Повтор с тем же ключом и входными данными возвращает существующий заказ даже после истечения котировки. Клиент повторно спрашивает согласие при изменении котировки.

Гость может включить уведомление о готовности конкретного заказа через `GET/PUT/DELETE /orders/{id}/pickup-alert` с идентификатором установки. Сервер разрешает подписку для оплаченных заказов на этапах «Принят» и «Готовится» и ставит уведомление в очередь при переходе в «Готов». [Уведомления о готовности](../server/docs/PICKUP_ALERTS.md)

Менеджер меняет приём новых заказов и стоп-лист своей точки через `/operator/availability`. Запись сверяет версию каталога и публикует новую версию при фактическом изменении. Котировки для остановленных позиций или закрытой точки проходят повторную серверную проверку перед заказом. [Каталог и доступность](../server/docs/CATALOG.md)

Предельная сумма всей корзины — 2 147 483 647 RWF. Большая сумма отклоняется с `400 invalid_input` до сохранения новой котировки, создания заказа или регистрации попытки оплаты. Сервер проверяет это ограничение и для ранее записанных котировок и заказов.

Сервер фиксирует попытку оплаты перед созданием платёжной ссылки. При неопределённом ответе провайдера клиент сохраняет прежний ключ и запрашивает исходный заказ. Статус подтверждается защищённым запросом сервера к Flutterwave по идентификатору транзакции или попытки. Отклонение отдельной транзакции на открытой платёжной странице сохраняет ту же попытку. Оплата, подтверждённая после истечения брони, попадает на разбор с состоянием `refund_pending`.

Тот же контракт включает вход оператора, очередь оплаченных заказов, переходы кухни и выдачи, раздел сверки платежей для менеджера и webhook Flutterwave Standard V3. Восстановление одной покупки на другом устройстве выдаёт доступ к просмотру и повтору по номеру заказа и подтверждённому телефону. Платёжные действия принадлежат исходной сессии. [Панель ресторана](../server/docs/OPERATIONS.md) · [Платёжный контур](../server/docs/PAYMENTS.md)

Менеджер своей точки может отменить оплаченный заказ до выдачи. Покупатель видит отмену и отдельный статус возврата. Сервер добавляет исходную оплату в сверку и переводит её в `refunded` после подтверждения полного возврата по этой транзакции. [Отмена заказа](../server/docs/OPERATIONS.md#отмена-до-выдачи)

Операторская очередь передаёт время сервера и время подтверждённого перехода оплаченного заказа в `accepted`. Для старых заказов время перехода может быть пустым. Заказ считается принятым кухней после сохранённого перехода в `preparing`. [Сигналы кухни](../server/docs/OPERATIONS.md#сигналы-кухни)

Менеджер может прикрепить оригинал чека от EBM продавца и подтвердить уже выполненный возврат через Flutterwave. Покупателю документ отдаётся по авторизованному маршруту заказа. Для публикации нужны отдельно настроенные данные точки, реквизиты Flutterwave, публичный HTTPS-адрес, правила возврата приложения и изолированный контур SMS. Профиль покупателя, отзыв по запросу пользователя и автоматическое формирование фискального чека требуют отдельных возможностей.

## Ответы об ошибках

Сервер использует `application/problem+json`. Клиент распознаёт тип ошибки по стабильному URI в `type`. `status` повторяет HTTP-статус, а `code` сопоставляет известный тип с сообщением и действием клиента. Клиент игнорирует незнакомые расширения. [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html)

`400` обозначает неверный ввод, `401` — отсутствующую или недействительную сессию, `404` — недоступный ресурс, `409` — конфликт с текущим состоянием и `503` — временный сбой. Для чужого и отсутствующего заказа используется одинаковый `404`. Тела ошибок содержат безопасное описание без контактных данных, токена и кода выдачи.
